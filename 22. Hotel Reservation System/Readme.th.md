# บทที่ 22: ระบบจองโรงแรม (Hotel Reservation System)

## บทนำ
ในบทนี้ เราจะออกแบบ**ระบบจองโรงแรม (Hotel Reservation System)** ซึ่งมีลักษณะคล้ายกับ Marriott International

สามารถนำไปประยุกต์ใช้กับระบบประเภทอื่นได้เช่นกัน - Airbnb, การจองเที่ยวบิน, การจองตั๋วหนัง

## ขั้นตอนที่ 1: ทำความเข้าใจปัญหาและกำหนดขอบเขตการออกแบบ (Understand the Problem and Establish Design Scope)
ก่อนที่จะเริ่มออกแบบระบบ เราควรถามคำถามกับผู้สัมภาษณ์เพื่อชี้แจงขอบเขตของระบบ:
 - C: ระบบมีขนาดเท่าใด?
 - I: เรากำลังสร้างเว็บไซต์สำหรับเครือโรงแรมที่มีโรงแรม 5,000 แห่ง และห้องพัก 1 ล้านห้อง
 - C: ลูกค้าชำระเงินตอนที่ทำการจอง หรือตอนที่มาถึงโรงแรม?
 - I: ลูกค้าชำระเงินเต็มจำนวนตอนที่ทำการจอง
 - C: ลูกค้าจองห้องพักผ่านเว็บไซต์เท่านั้นหรือไม่? เราต้องรองรับช่องทางการจองอื่น ๆ เช่นการโทรศัพท์ด้วยหรือไม่?
 - I: ลูกค้าทำการจองผ่านเว็บไซต์หรือแอปเท่านั้น
 - C: ลูกค้าสามารถยกเลิกการจองได้หรือไม่?
 - I: ได้
 - C: มีสิ่งอื่นใดที่ต้องพิจารณาอีกหรือไม่?
 - I: มี เราอนุญาตให้มีการ overbooking ได้ 10% โรงแรมจะขายห้องพักมากกว่าจำนวนที่มีอยู่จริง โรงแรมทำเช่นนี้เพราะคาดการณ์ว่าลูกค้าบางส่วนจะยกเลิกการจอง
 - C: เนื่องจากมีเวลาไม่มากนัก เราจะเน้นไปที่ - หน้าแสดงข้อมูลโรงแรม, หน้ารายละเอียดห้องพัก, การจองห้องพัก, แผงควบคุมสำหรับผู้ดูแลระบบ (admin panel), การรองรับ overbooking
 - I: ฟังดูดี
 - I: มีอีกเรื่องหนึ่ง - ราคาโรงแรมมีการเปลี่ยนแปลงอยู่ตลอดเวลา สมมติว่าราคาห้องพักของโรงแรมเปลี่ยนแปลงทุกวัน
 - C: ตกลง

### **ความต้องการที่ไม่ใช่เชิงฟังก์ชัน (Non-functional requirements)**
 - รองรับ concurrency สูง - อาจมีลูกค้าจำนวนมากพยายามจองโรงแรมเดียวกันในช่วงฤดูกาลท่องเที่ยวสูงสุด (peak season)
 - latency ระดับปานกลาง - เป็นการดีที่จะมี latency ต่ำเมื่อผู้ใช้ทำการจอง แต่ก็ยอมรับได้หากระบบใช้เวลาสองสามวินาทีในการประมวลผล

### **การประมาณการคร่าว ๆ (Back-of-the-envelope estimation)**
 - โรงแรม 5,000 แห่ง และห้องพักรวม 1 ล้านห้อง
 - สมมติว่าห้องพัก 70% มีผู้เข้าพัก และระยะเวลาพักเฉลี่ยอยู่ที่ 3 วัน
 - จำนวนการจองต่อวันโดยประมาณ - 1 ล้าน * 0.7 / 3 = ประมาณ 240,000 การจองต่อวัน
 - จำนวนการจองต่อวินาที - 240,000 / 10^5 วินาทีต่อวัน = ประมาณ 3 การจอง โดยเฉลี่ย TPS ของการจองอยู่ในระดับต่ำ

มาลองประมาณค่า QPS กัน หากเราสมมติว่ามี 3 ขั้นตอนกว่าจะถึงหน้าจอง และแต่ละหน้ามีอัตราการ conversion อยู่ที่ 10%
เราสามารถประมาณได้ว่า หากมีการจอง 3 ครั้ง จะต้องมีการเข้าชมหน้าจอง 30 ครั้ง และการเข้าชมหน้ารายละเอียดห้องพัก 300 ครั้ง

## ขั้นตอนที่ 2: นำเสนอการออกแบบระดับสูงและขอความเห็นชอบ (Propose High-Level Design and Get Buy-In)
เราจะสำรวจ - การออกแบบ API, Data model, การออกแบบระดับสูง (high-level design)

### **การออกแบบ API (API Design)**
การออกแบบ API นี้เน้นไปที่ endpoint หลัก ๆ (โดยใช้แนวปฏิบัติแบบ RESTful) ที่เราจำเป็นต้องมีเพื่อรองรับระบบจองโรงแรม

ระบบที่สมบูรณ์เต็มรูปแบบจะต้องการ API ที่กว้างขวางกว่านี้ ซึ่งรองรับการค้นหาห้องพักตามเงื่อนไขต่าง ๆ มากมาย แต่เราจะไม่เน้นในส่วนนั้นในบทนี้
เหตุผลก็คือส่วนเหล่านั้นไม่ได้มีความท้าทายทางเทคนิคมากนัก จึงอยู่นอกขอบเขตของบทนี้

**API เกี่ยวกับโรงแรม (Hotel-related API)**
 - `GET /v1/hotels/{id}` - ดึงข้อมูลรายละเอียดเกี่ยวกับโรงแรม
 - `POST /v1/hotels` - เพิ่มโรงแรมใหม่ ใช้ได้เฉพาะฝ่ายปฏิบัติการ (ops) เท่านั้น
 - `PUT /v1/hotels/{id}` - อัปเดตข้อมูลโรงแรม ใช้ได้เฉพาะฝ่ายปฏิบัติการเท่านั้น
 - `DELETE /v1/hotels/{id}` - ลบโรงแรม API นี้ใช้ได้เฉพาะฝ่ายปฏิบัติการเท่านั้น

**API เกี่ยวกับห้องพัก (Room-related API)**
 - `GET /v1/hotels/{id}/rooms/{id}` - ดึงข้อมูลรายละเอียดเกี่ยวกับห้องพัก
 - `POST /v1/hotels/{id}/rooms` - เพิ่มห้องพัก ใช้ได้เฉพาะฝ่ายปฏิบัติการเท่านั้น
 - `PUT /v1/hotels/{id}/rooms/{id}` - อัปเดตข้อมูลห้องพัก ใช้ได้เฉพาะฝ่ายปฏิบัติการเท่านั้น
 - `DELETE /v1/hotels/{id}/rooms/{id}` - ลบห้องพัก ใช้ได้เฉพาะฝ่ายปฏิบัติการเท่านั้น

**API เกี่ยวกับการจอง (Reservation-related API)**
 - `GET /v1/reservations` - ดึงประวัติการจองของผู้ใช้ปัจจุบัน
 - `GET /v1/reservations/{id}` - ดึงข้อมูลรายละเอียดเกี่ยวกับการจอง
 - `POST /v1/reservations` - ทำการจองใหม่
 - `DELETE /v1/reservations/{id}` - ยกเลิกการจอง

นี่คือตัวอย่างคำขอ (request) สำหรับการทำการจอง:

```
{
  "startDate":"2021-04-28",
  "endDate":"2021-04-30",
  "hotelID":"245",
  "roomID":"U12354673389",
  "reservationID":"13422445"
}
```

โปรดสังเกตว่า `reservationID` เป็น idempotency key เพื่อป้องกันการจองซ้ำซ้อน (double booking) รายละเอียดจะอธิบายไว้ใน[หัวข้อเรื่อง concurrency](#concurrency-issues)

### **Data model**
ก่อนที่เราจะเลือกฐานข้อมูลที่จะใช้ ลองพิจารณารูปแบบการเข้าถึงข้อมูล (access patterns) ของเรากันก่อน

เราจำเป็นต้องรองรับ query ต่อไปนี้:
 - ดูข้อมูลรายละเอียดเกี่ยวกับโรงแรม
 - ค้นหาประเภทห้องพักที่ว่างในช่วงวันที่ที่กำหนด
 - บันทึกการจอง
 - ค้นหาการจองหรือประวัติการจองที่ผ่านมา

จากการประมาณการของเรา เราทราบว่าขนาดของระบบไม่ได้ใหญ่มากนัก แต่เราต้องเตรียมพร้อมสำหรับทราฟฟิกที่พุ่งสูงขึ้น

จากความรู้นี้ เราจะเลือกใช้ฐานข้อมูลเชิงสัมพันธ์ (relational database) เพราะ:
 - ฐานข้อมูลเชิงสัมพันธ์ทำงานได้ดีกับระบบที่มีการอ่านมาก (read-heavy) และมีการเขียนน้อย (less write-heavy)
 - ฐานข้อมูล NoSQL มักจะถูกปรับให้เหมาะสม (optimize) สำหรับการเขียน แต่เราทราบว่าเราจะไม่มีการเขียนมากนัก เนื่องจากมีเพียงส่วนน้อยของผู้ที่เข้าชมเว็บไซต์เท่านั้นที่จะทำการจอง
 - ฐานข้อมูลเชิงสัมพันธ์ให้การรับประกันแบบ ACID ซึ่งมีความสำคัญมากสำหรับระบบเช่นนี้ เพราะหากไม่มีการรับประกันนี้ เราจะไม่สามารถป้องกันปัญหาต่าง ๆ เช่น ยอดเงินติดลบ, การเรียกเก็บเงินซ้ำซ้อน ฯลฯ ได้
 - ฐานข้อมูลเชิงสัมพันธ์สามารถสร้างแบบจำลองข้อมูล (model) ได้อย่างง่ายดาย เนื่องจากโครงสร้างมีความชัดเจนมาก

### **การออกแบบระดับสูง (High-level Design)**
เราเลือกใช้สถาปัตยกรรมแบบ microservice สำหรับการออกแบบนี้ ซึ่งเป็นที่นิยมอย่างมากในช่วงไม่กี่ปีที่ผ่านมา:

<div style="margin-left:3rem">
    <img src="./images/high-level-design.png" alt="high-level-design" width="500" />
</div>

 - **ผู้ใช้ (Users)**: จองห้องพักผ่านโทรศัพท์หรือคอมพิวเตอร์
 - **ผู้ดูแลระบบ (Admin)**: ทำหน้าที่ด้านการบริหารจัดการ เช่น การคืนเงิน/ยกเลิกการชำระเงิน ฯลฯ
 - **CDN**: แคช static resource ต่าง ๆ เช่น JS bundle, รูปภาพ, วิดีโอ ฯลฯ
 - **Public API Gateway**: บริการที่มีการจัดการเต็มรูปแบบ (fully-managed) ซึ่งรองรับ rate limiting, การยืนยันตัวตน (authentication) ฯลฯ
 - **Internal APIs**: มองเห็นได้เฉพาะบุคลากรที่ได้รับอนุญาตเท่านั้น มักจะได้รับการปกป้องด้วย VPN
 - **Hotel service**: ให้ข้อมูลรายละเอียดเกี่ยวกับโรงแรมและห้องพัก ข้อมูลโรงแรมและห้องพักเป็นข้อมูล static จึงสามารถแคชได้อย่างจริงจัง (aggressively)
 - **Rate service**: ให้ข้อมูลราคาห้องพักสำหรับวันที่ในอนาคตต่าง ๆ ข้อสังเกตที่น่าสนใจเกี่ยวกับ domain นี้คือ ราคาขึ้นอยู่กับว่าโรงแรมเต็มมากน้อยเพียงใดในวันนั้น ๆ
 - **Reservation service**: รับคำขอการจองและทำการจองห้องพัก อีกทั้งยังติดตาม inventory ของห้องพักเมื่อมีการจอง/ยกเลิกการจองเกิดขึ้น
 - **Payment service**: ประมวลผลการชำระเงินและอัปเดตสถานะการจองเมื่อสำเร็จ
 - **Hotel management service**: ใช้ได้เฉพาะบุคลากรที่ได้รับอนุญาตเท่านั้น อนุญาตให้ทำฟังก์ชันด้านการบริหารบางอย่าง สำหรับการจัดการและดูข้อมูลการจอง, โรงแรม ฯลฯ

การสื่อสารระหว่างบริการ (inter-service communication) สามารถทำได้ผ่าน RPC framework เช่น gRPC

## ขั้นตอนที่ 3: เจาะลึกการออกแบบ (Design Deep Dive)
มาเจาะลึกในเรื่องต่อไปนี้:
 - Data model ที่ปรับปรุงแล้ว
 - ปัญหาเรื่อง concurrency
 - ความสามารถในการขยายระบบ (Scalability)
 - การแก้ไขปัญหาความไม่สอดคล้องของข้อมูล (data inconsistency) ใน microservices

### **Data model ที่ปรับปรุงแล้ว (Improved data model)**
ตามที่กล่าวไว้ในหัวข้อก่อนหน้า เราจำเป็นต้องแก้ไข API และ schema ของเรา เพื่อให้สามารถจองประเภทของห้องพักแทนที่จะจองห้องพักที่เจาะจงได้

สำหรับ reservation API เราจะไม่จอง `roomID` อีกต่อไป แต่จะจอง `roomTypeID` แทน:

```
POST /v1/reservations
{
  "startDate":"2021-04-28",
  "endDate":"2021-04-30",
  "hotelID":"245",
  "roomTypeID":"12354673389",
  "roomCount":"3",
  "reservationID":"13422445"
}
```

นี่คือ schema ที่อัปเดตแล้ว:

<div style="margin-left:3rem">
    <img src="./images/updated-schema.png" alt="updated-schema" width="500" />
</div>

 - **room**: เก็บข้อมูลเกี่ยวกับห้องพัก
 - **room_type_rate**: เก็บข้อมูลเกี่ยวกับราคาสำหรับประเภทห้องพักหนึ่ง ๆ
 - **reservation**: บันทึกข้อมูลการจองของผู้เข้าพัก
 - **room_type_inventory**: เก็บข้อมูล inventory เกี่ยวกับห้องพักของโรงแรม

มาดูคอลัมน์ต่าง ๆ ของ `room_type_inventory` กันเพราะตารางนี้น่าสนใจกว่า:
 - **hotel_id**: id ของโรงแรม
 - **room_type_id**: id ของประเภทห้องพัก
 - **date**: วันที่หนึ่งวัน
 - **total_inventory**: จำนวนห้องพักทั้งหมด ลบด้วยจำนวนห้องที่ถูกดึงออกจาก inventory ชั่วคราว
 - **total_reserved**: จำนวนห้องทั้งหมดที่ถูกจองสำหรับ (hotel_id, room_type_id, date) ที่กำหนด

มีวิธีอื่น ๆ ในการออกแบบตารางนี้ แต่การมีหนึ่งแถวต่อหนึ่ง (hotel_id, room_type_id, date) 
ช่วยให้การจัดการการจองและการทำ query ทำได้ง่ายขึ้น

แถวในตารางนี้จะถูกเติมข้อมูลล่วงหน้าโดยใช้ daily CRON job

| 2210     | 101          | 2021-06-01 | 30              | 23             |
| 2210     | 101          | 2021-06-02 | 30              | 25             |

ตัวอย่าง SQL query เพื่อตรวจสอบความว่างของประเภทห้องพัก:

```
SELECT date, total_inventory, total_reserved
FROM room_type_inventory
WHERE room_type_id = ${roomTypeId} AND hotel_id = ${hotelId}
AND date between ${startDate} and ${endDate}
```

วิธีตรวจสอบความว่างสำหรับจำนวนห้องพักที่ระบุโดยใช้ข้อมูลนั้น (โปรดสังเกตว่าเรารองรับการ overbooking):

```
if (total_reserved + ${numberOfRoomsToReserve}) <= 110% * total_inventory
```

ทีนี้มาลองประมาณการปริมาณ storage กันบ้าง
 - เรามีโรงแรม 5,000 แห่ง
 - แต่ละโรงแรมมีประเภทห้องพัก 20 ประเภท
 - 5,000 * 20 * 2 (ปี) * 365 (วัน) = 73 ล้านแถว

73 ล้านแถวไม่ใช่ข้อมูลปริมาณมากนัก และเซิร์ฟเวอร์ฐานข้อมูลตัวเดียวก็สามารถรับมือได้
อย่างไรก็ตาม การตั้งค่า read replication (ซึ่งอาจกระจายข้ามหลาย zone) ก็สมเหตุสมผล เพื่อให้มีความพร้อมใช้งานสูง (high availability)

คำถามต่อเนื่อง - หากข้อมูลการจองมีขนาดใหญ่เกินกว่าจะเก็บในฐานข้อมูลเดียวได้ เราจะทำอย่างไร?
 - เก็บเฉพาะข้อมูลการจองปัจจุบันและอนาคต ประวัติการจองสามารถย้ายไปเก็บใน cold storage ได้
 - การทำ database sharding - เราสามารถ shard ข้อมูลโดยใช้ `hash(hotel_id) % servers_cnt` เนื่องจากเราจะเลือก `hotel_id` เสมอใน query ของเรา

### **ปัญหาเรื่อง Concurrency (Concurrency issues)**
อีกปัญหาสำคัญที่ต้องแก้ไขคือการจองซ้ำซ้อน (double booking)

มีสองประเด็นที่ต้องแก้ไข:
 - ผู้ใช้คนเดียวกันคลิก "จอง" สองครั้ง
 - ผู้ใช้หลายคนพยายามจองห้องพักในเวลาเดียวกัน

นี่คือภาพจำลองของปัญหาแรก:

<div style="margin-left:3rem">
    <img src="./images/double-booking-single-user.png" alt="double-booking-single-user" width="500" />
</div>

มีสองแนวทางในการแก้ไขปัญหานี้:
 - การจัดการฝั่ง client (Client-side handling) - front-end สามารถปิดการใช้งานปุ่มจองได้เมื่อถูกคลิกแล้ว อย่างไรก็ตาม หากผู้ใช้ปิดการใช้งาน JavaScript พวกเขาก็จะไม่เห็นปุ่มเปลี่ยนเป็นสีเทา
 - API แบบ Idempotent - เพิ่ม idempotency key เข้าไปใน API ซึ่งช่วยให้ผู้ใช้สามารถดำเนินการอย่างใดอย่างหนึ่งได้เพียงครั้งเดียว ไม่ว่า endpoint จะถูกเรียกกี่ครั้งก็ตาม:

<div style="margin-left:3rem">
    <img src="./images/idempotency.png" alt="idempotency" width="500" />
</div>

นี่คือวิธีการทำงานของขั้นตอนนี้:
 - คำสั่งจอง (reservation order) จะถูกสร้างขึ้นทันทีที่คุณเริ่มกรอกรายละเอียดและทำการจอง คำสั่งจองนี้จะถูกสร้างขึ้นโดยใช้ตัวระบุที่ไม่ซ้ำกันทั่วโลก (globally unique identifier)
 - ส่งการจองครั้งที่ 1 โดยใช้ `reservation_id` ที่สร้างขึ้นในขั้นตอนก่อนหน้า
 - หากมีการคลิก "ยืนยันการจอง" เป็นครั้งที่สอง `reservation_id` เดียวกันจะถูกส่งไป และฝั่ง backend จะตรวจพบว่านี่เป็นการจองที่ซ้ำซ้อน
 - การซ้ำซ้อนนี้จะถูกป้องกันโดยการทำให้คอลัมน์ `reservation_id` มี unique constraint ซึ่งป้องกันไม่ให้มีการเก็บหลายเรคคอร์ดที่มี id เดียวกันในฐานข้อมูล

<div style="margin-left:3rem">
    <img src="./images/unique-constraint-violation.png" alt="unique-constraint-violation" width="500" />
</div>

แล้วถ้ามีผู้ใช้หลายคนทำการจองเดียวกันล่ะ?

<div style="margin-left:3rem">
    <img src="./images/double-booking-multiple-users.png" alt="double-booking-multiple-users" width="500" />
</div>

 - สมมติว่าระดับ transaction isolation ไม่ใช่ serializable
 - ผู้ใช้ 1 และ 2 พยายามจองห้องพักเดียวกันในเวลาเดียวกัน
 - Transaction 1 ตรวจสอบว่ามีห้องพักเพียงพอหรือไม่ - มีเพียงพอ
 - Transaction 2 ตรวจสอบว่ามีห้องพักเพียงพอหรือไม่ - มีเพียงพอ
 - Transaction 2 จองห้องพักและอัปเดต inventory
 - Transaction 1 ก็จองห้องพักด้วยเช่นกัน เนื่องจากยังคงเห็นว่ามี `total_reserved` อยู่ที่ 99 ห้อง จากทั้งหมด 100 ห้อง
 - ทั้งสอง transaction commit การเปลี่ยนแปลงสำเร็จทั้งคู่

ปัญหานี้สามารถแก้ไขได้โดยใช้กลไก locking บางรูปแบบ:
 - Pessimistic locking
 - Optimistic locking
 - Database constraints

นี่คือ SQL ที่เราใช้ในการจองห้องพัก:

```sql
# step 1: check room inventory
SELECT date, total_inventory, total_reserved
FROM room_type_inventory
WHERE room_type_id = ${roomTypeId} AND hotel_id = ${hotelId}
AND date between ${startDate} and ${endDate}

# For every entry returned from step 1
if((total_reserved + ${numberOfRoomsToReserve}) > 110% * total_inventory) {
  Rollback
}

# step 2: reserve rooms
UPDATE room_type_inventory
SET total_reserved = total_reserved + ${numberOfRoomsToReserve}
WHERE room_type_id = ${roomTypeId}
AND date between ${startDate} and ${endDate}

Commit
```

#### ทางเลือกที่ 1: Pessimistic locking
Pessimistic locking ป้องกันการอัปเดตพร้อมกันโดยการใส่ lock บนเรคคอร์ดขณะที่กำลังถูกอัปเดต

วิธีนี้สามารถทำได้ใน MySQL โดยใช้ query `SELECT... FOR UPDATE` ซึ่งจะ lock แถวที่ query เลือกไว้จนกว่า transaction จะถูก commit

<div style="margin-left:3rem">
    <img src="./images/pessimistic-locking.png" alt="pessimistic-locking" width="500" />
</div>

ข้อดี:
 - ป้องกันไม่ให้แอปพลิเคชันอัปเดตข้อมูลที่กำลังถูกเปลี่ยนแปลงอยู่
 - ง่ายต่อการนำไปใช้งาน และหลีกเลี่ยงข้อขัดแย้ง (conflict) โดยการทำ serialize การอัปเดต มีประโยชน์เมื่อมีการแย่งใช้ข้อมูล (data contention) สูง

ข้อเสีย:
 - อาจเกิด deadlock ได้ เมื่อมีการล็อกทรัพยากรหลายรายการพร้อมกัน
 - แนวทางนี้ไม่สามารถขยายได้ดี (not scalable) - หาก transaction ถูก lock ไว้นานเกินไป จะส่งผลกระทบต่อ transaction อื่น ๆ ที่พยายามเข้าถึงทรัพยากรนั้น
 - ผลกระทบจะรุนแรงขึ้นเมื่อ query เลือกทรัพยากรจำนวนมาก และ transaction มีอายุยืนยาว

ผู้เขียนไม่แนะนำแนวทางนี้เนื่องจากปัญหาด้านความสามารถในการขยาย (scalability)

#### ทางเลือกที่ 2: Optimistic locking
Optimistic locking อนุญาตให้ผู้ใช้หลายคนพยายามอัปเดตเรคคอร์ดในเวลาเดียวกันได้

มีสองวิธีที่นิยมใช้ในการนำไปใช้งาน - หมายเลขเวอร์ชัน (version numbers) และ timestamp แนะนำให้ใช้หมายเลขเวอร์ชันเนื่องจากนาฬิกาของเซิร์ฟเวอร์อาจไม่แม่นยำ

<div style="margin-left:3rem">
    <img src="./images/optimistic-locking.png" alt="optimistic-locking" width="500" />
</div>

 - เพิ่มคอลัมน์ `version` ใหม่เข้าไปในตารางฐานข้อมูล
 - ก่อนที่ผู้ใช้จะแก้ไขแถวในฐานข้อมูล จะมีการอ่านหมายเลขเวอร์ชันก่อน
 - เมื่อผู้ใช้อัปเดตแถวนั้น หมายเลขเวอร์ชันจะเพิ่มขึ้น 1 และเขียนกลับไปยังฐานข้อมูล
 - การตรวจสอบ (validation) ของฐานข้อมูลจะป้องกันการ insert หากหมายเลขเวอร์ชันใหม่ไม่มากกว่าเวอร์ชันก่อนหน้า

Optimistic locking โดยทั่วไปจะเร็วกว่า pessimistic locking เนื่องจากเราไม่ได้ lock ฐานข้อมูล
อย่างไรก็ตาม ประสิทธิภาพของมันจะลดลงเมื่อ concurrency สูง เนื่องจากทำให้เกิดการ rollback จำนวนมาก

ข้อดี:
 - ป้องกันไม่ให้แอปพลิเคชันแก้ไขข้อมูลที่ล้าสมัย (stale data)
 - เราไม่จำเป็นต้อง acquire lock ในฐานข้อมูล
 - เป็นตัวเลือกที่แนะนำเมื่อมีการแย่งใช้ข้อมูลต่ำ กล่าวคือแทบจะไม่มี update conflict เกิดขึ้น

ข้อเสีย:
 - ประสิทธิภาพแย่เมื่อมีการแย่งใช้ข้อมูลสูง

Optimistic locking เป็นตัวเลือกที่ดีสำหรับระบบของเรา เนื่องจาก QPS ของการจองไม่ได้สูงมากนัก

#### ทางเลือกที่ 3: Database constraints
แนวทางนี้คล้ายคลึงกับ optimistic locking มาก แต่การป้องกัน (guardrails) จะถูกนำไปใช้งานผ่าน database constraint:

```
CONSTRAINT `check_room_count` CHECK((`total_inventory - total_reserved` >= 0))
```

<div style="margin-left:3rem">
    <img src="./images/database-constraint.png" alt="database-constraint" width="500" />
</div>

ข้อดี:
 - ง่ายต่อการนำไปใช้งาน
 - ทำงานได้ดีเมื่อมีการแย่งใช้ข้อมูลน้อย

ข้อเสีย:
 - คล้ายกับ optimistic locking คือทำงานได้ไม่ดีเมื่อมีการแย่งใช้ข้อมูลสูง
 - Database constraint ไม่สามารถทำ version control ได้ง่ายเหมือนกับโค้ดของแอปพลิเคชัน
 - ไม่ใช่ทุกฐานข้อมูลที่รองรับ constraint

นี่คือตัวเลือกที่ดีอีกตัวสำหรับระบบจองโรงแรม เนื่องจากง่ายต่อการนำไปใช้งาน

### **ความสามารถในการขยายระบบ (Scalability)**
โดยทั่วไปแล้ว ปริมาณโหลดของระบบจองโรงแรมจะไม่สูงมากนัก

อย่างไรก็ตาม ผู้สัมภาษณ์อาจถามว่าคุณจะจัดการอย่างไรในสถานการณ์ที่ระบบถูกนำไปใช้กับเว็บไซต์ท่องเที่ยวที่ใหญ่กว่าและได้รับความนิยม เช่น booking.com
ในกรณีนั้น QPS อาจสูงกว่าเดิมถึง 1,000 เท่า

เมื่อเกิดสถานการณ์เช่นนี้ สิ่งสำคัญคือต้องเข้าใจว่าคอขวด (bottleneck) ของเราอยู่ที่ใด บริการทั้งหมดเป็นแบบ stateless จึงสามารถขยายได้ง่ายโดยการทำ replication

อย่างไรก็ตาม ฐานข้อมูลเป็นแบบ stateful และไม่ชัดเจนนักว่าจะขยายได้อย่างไร

วิธีหนึ่งในการขยายคือการทำ database sharding - เราสามารถแบ่งข้อมูลออกไปยังฐานข้อมูลหลายตัว โดยแต่ละตัวจะมีข้อมูลเพียงส่วนหนึ่งเท่านั้น

เราสามารถ shard โดยใช้ `hotel_id` ได้ เนื่องจากทุก query จะกรองข้อมูลด้วยฟิลด์นี้
สมมติว่า QPS อยู่ที่ 30,000 หลังจากทำการ shard ฐานข้อมูลออกเป็น 16 shard แล้ว แต่ละ shard จะรับภาระ 1,875 QPS ซึ่งอยู่ในขีดความสามารถของ MySQL cluster เดียว

<div style="margin-left:3rem">
    <img src="./images/database-sharding.png" alt="database-sharding" width="500" />
</div>

เรายังสามารถใช้การแคช (caching) สำหรับข้อมูล inventory ห้องพักและการจองผ่าน Redis ได้ด้วย เราสามารถตั้งค่า TTL เพื่อให้ข้อมูลเก่าหมดอายุสำหรับวันที่ที่ผ่านไปแล้วได้

<div style="margin-left:3rem">
    <img src="./images/inventory-cache.png" alt="inventory-cache" width="500" />
</div>

วิธีที่เราจัดเก็บ inventory จะขึ้นอยู่กับ `hotel_id`, `room_type_id` และ `date`:

```
key: hotelID_roomTypeID_{date}
value: the number of available rooms for the given hotel ID, room type ID and date.
```

ความสอดคล้องของข้อมูล (data consistency) เกิดขึ้นแบบ async และถูกจัดการโดยใช้กลไก CDC streaming - การเปลี่ยนแปลงในฐานข้อมูลจะถูกอ่านและนำไปใช้กับระบบอื่นแยกต่างหาก
Debezium เป็นตัวเลือกที่นิยมใช้สำหรับการซิงค์การเปลี่ยนแปลงของฐานข้อมูลกับ Redis

เมื่อใช้กลไกเช่นนี้ มีความเป็นไปได้ที่ cache และฐานข้อมูลจะไม่สอดคล้องกันในช่วงเวลาหนึ่ง
ซึ่งไม่เป็นปัญหาในกรณีของเรา เพราะฐานข้อมูลจะป้องกันไม่ให้เราทำการจองที่ไม่ถูกต้องได้

สิ่งนี้จะทำให้เกิดปัญหาบางอย่างบน UI เนื่องจากผู้ใช้จะต้อง refresh หน้าเพื่อจะเห็นว่า "ไม่มีห้องว่างแล้ว"
แต่นั่นก็เป็นสิ่งที่สามารถเกิดขึ้นได้อยู่แล้วไม่ว่าจะมีปัญหานี้หรือไม่ เช่น หากคนคนหนึ่งลังเลอยู่นานก่อนที่จะทำการจอง

ข้อดีของการแคช:
 - ลดภาระของฐานข้อมูล
 - ประสิทธิภาพสูง เนื่องจาก Redis จัดการข้อมูลแบบ in-memory

ข้อเสียของการแคช:
 - การรักษาความสอดคล้องของข้อมูลระหว่าง cache และฐานข้อมูลนั้นยาก เราต้องพิจารณาว่าความไม่สอดคล้องนี้ส่งผลกระทบต่อประสบการณ์ผู้ใช้อย่างไร

### **ความสอดคล้องของข้อมูลระหว่างบริการ (Data consistency among services)**
แอปพลิเคชันแบบ monolithic ช่วยให้เราสามารถใช้ฐานข้อมูลเชิงสัมพันธ์ที่ใช้งานร่วมกัน (shared) เพื่อรับประกันความสอดคล้องของข้อมูลได้

ในการออกแบบ microservice ของเรา เราเลือกใช้แนวทางแบบผสมผสาน (hybrid) โดยบางบริการแยกออกจากกัน 
แต่ reservation API และ inventory API จะถูกจัดการโดยบริการเดียวกัน

สิ่งนี้ทำเพื่อให้เราสามารถใช้ประโยชน์จากการรับประกันแบบ ACID ของฐานข้อมูลเชิงสัมพันธ์ เพื่อรับประกันความสอดคล้อง

อย่างไรก็ตาม ผู้สัมภาษณ์อาจท้าทายแนวทางนี้ เนื่องจากมันไม่ใช่สถาปัตยกรรม microservice แบบบริสุทธิ์ ซึ่งแต่ละบริการควรมีฐานข้อมูลเฉพาะของตนเอง:

<div style="margin-left:3rem">
    <img src="./images/microservices-vs-monolith.png" alt="microservices-vs-monolith" width="500" />
</div>

สิ่งนี้อาจนำไปสู่ปัญหาความสอดคล้องของข้อมูล ในเซิร์ฟเวอร์แบบ monolithic เราสามารถใช้ประโยชน์จากความสามารถด้าน transaction ของฐานข้อมูลเชิงสัมพันธ์ เพื่อทำ operation แบบ atomic ได้:

<div style="margin-left:3rem">
    <img src="./images/atomicity-monolith.png" alt="atomicity-monolith" width="500" />
</div>

อย่างไรก็ตาม การรับประกันความเป็น atomic นี้จะท้าทายมากขึ้น เมื่อ operation ครอบคลุมหลายบริการ:

<div style="margin-left:3rem">
    <img src="./images/microservice-non-atomic-operation.png" alt="microservice-non-atomic-operation" width="500" />
</div>

มีเทคนิคที่รู้จักกันดีบางส่วนสำหรับจัดการกับความไม่สอดคล้องของข้อมูลเหล่านี้:
 - **Two-phase commit**: โปรโตคอลฐานข้อมูลที่รับประกัน atomic transaction commit ข้ามหลายโหนด 
   อย่างไรก็ตาม วิธีนี้ไม่มีประสิทธิภาพนัก เนื่องจากความล่าช้าของโหนดเดียวจะทำให้ทุกโหนดต้อง block operation
 - **Saga**: ลำดับของ local transaction ซึ่งจะมีการทำ compensating transaction เมื่อขั้นตอนใดขั้นตอนหนึ่งใน workflow ล้มเหลว นี่เป็นแนวทางที่ให้ความสอดคล้องแบบ eventually consistent

ควรสังเกตว่าการแก้ไขปัญหาความไม่สอดคล้องของข้อมูลข้าม microservice นั้นเป็นปัญหาที่ท้าทาย ซึ่งเพิ่มความซับซ้อนให้กับระบบ
เป็นเรื่องดีที่จะพิจารณาว่าต้นทุนนี้คุ้มค่าหรือไม่ เมื่อเทียบกับแนวทางที่เน้นความเรียบง่ายในทางปฏิบัติของเรา ที่รวม operation ที่พึ่งพากันไว้ในฐานข้อมูลเชิงสัมพันธ์เดียวกัน

## ขั้นตอนที่ 4: สรุป (Wrap Up)
เรานำเสนอการออกแบบระบบจองโรงแรม

นี่คือขั้นตอนต่าง ๆ ที่เราได้ผ่านมา:
 - รวบรวมความต้องการและทำการประมาณการคร่าว ๆ เพื่อทำความเข้าใจขนาดของระบบ
 - เรานำเสนอการออกแบบ API, Data Model และสถาปัตยกรรมของระบบใน high-level design
 - ในการเจาะลึก เราได้สำรวจการออกแบบ schema ฐานข้อมูลทางเลือกอื่น ๆ เมื่อความต้องการเปลี่ยนแปลงไป
 - เราได้พูดคุยเกี่ยวกับ race condition และเสนอแนวทางแก้ไข - pessimistic/optimistic locking, database constraint
 - แนวทางในการขยายระบบผ่าน database sharding และการแคช
 - สุดท้ายเราได้พูดถึงวิธีจัดการกับปัญหาความสอดคล้องของข้อมูลข้าม microservice หลายตัว
