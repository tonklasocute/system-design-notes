# บทที่ 26: ระบบชำระเงิน (Payment System)

## บทนำ
เราจะออกแบบ **ระบบชำระเงิน (payment system)** ในบทนี้ ซึ่งเป็นรากฐานของ **e-commerce** สมัยใหม่ทั้งหมด

**ระบบชำระเงิน (payment system)** ถูกใช้ในการชำระธุรกรรมทางการเงิน (settle financial transactions) โดยการโอนมูลค่าเงินตรา

## ขั้นตอนที่ 1: ทำความเข้าใจปัญหาและกำหนดขอบเขตการออกแบบ (Understand the Problem and Establish Design Scope)
 * C: เรากำลังสร้างระบบชำระเงินแบบไหน?
 * I: payment backend สำหรับระบบ e-commerce คล้ายกับ Amazon.com ซึ่งจัดการทุกอย่างที่เกี่ยวข้องกับการเคลื่อนย้ายเงิน
 * C: ระบบรองรับตัวเลือกการชำระเงินแบบใดบ้าง - บัตรเครดิต, PayPal, บัตรธนาคาร ฯลฯ?
 * I: ในชีวิตจริง ระบบควรรองรับตัวเลือกทั้งหมดนี้ แต่สำหรับวัตถุประสงค์ของการสัมภาษณ์นี้ เราจะใช้การชำระเงินผ่านบัตรเครดิต
 * C: เราประมวลผลบัตรเครดิตด้วยตัวเองหรือไม่?
 * I: ไม่ เราใช้ผู้ให้บริการภายนอก (third-party) เช่น Stripe, Braintree, Square เป็นต้น
 * C: เราจัดเก็บข้อมูลบัตรเครดิตไว้ในระบบของเราหรือไม่?
 * I: เนื่องด้วยเหตุผลด้านการปฏิบัติตามกฎระเบียบ (compliance) เราไม่จัดเก็บข้อมูลบัตรเครดิตโดยตรงในระบบของเรา เราพึ่งพาผู้ให้บริการประมวลผลการชำระเงินจากภายนอก (third-party payment processor)
 * C: แอปพลิเคชันนี้เป็นระบบระดับโลกหรือไม่? เราต้องรองรับสกุลเงินที่แตกต่างกันและการชำระเงินระหว่างประเทศหรือไม่?
 * I: แอปพลิเคชันนี้เป็นระดับโลก แต่เพื่อวัตถุประสงค์ของการสัมภาษณ์นี้ เราจะสมมติว่าใช้เพียงสกุลเงินเดียว
 * C: เรารองรับธุรกรรมการชำระเงินกี่ครั้งต่อวัน?
 * I: 1 ล้านธุรกรรมต่อวัน
 * C: เราจำเป็นต้องรองรับ flow การจ่ายเงินออก (payout) เช่น การจ่ายเงินให้ผู้รับเงินทุกเดือนหรือไม่?
 * I: ใช่ เราต้องรองรับสิ่งนั้น
 * C: มีอะไรอีกที่ฉันควรให้ความสนใจหรือไม่?
 * I: เราจำเป็นต้องรองรับการกระทบยอด (reconciliation) เพื่อแก้ไขความไม่สอดคล้องกันใด ๆ ในการสื่อสารกับระบบภายในและภายนอก

### **ความต้องการด้านฟังก์ชันการทำงาน (Functional requirements)**
 * Pay-in flow - ระบบชำระเงินรับเงินจากลูกค้าในนามของ merchant
 * Pay-out flow - ระบบชำระเงินส่งเงินให้ผู้ขายทั่วโลก

### **ความต้องการที่ไม่ใช่ฟังก์ชันการทำงาน (Non-functional requirements)**
 * ความน่าเชื่อถือ (reliability) และความทนทานต่อความล้มเหลว (fault-tolerance) การชำระเงินที่ล้มเหลวต้องได้รับการจัดการอย่างระมัดระวัง
 * ต้องมีการตั้งค่าการกระทบยอด (reconciliation) ระหว่างระบบภายในและภายนอก

### **การประมาณการแบบคร่าว ๆ (Back-of-the-envelope estimation)**
ระบบต้องประมวลผล 1 ล้านธุรกรรมต่อวัน ซึ่งเท่ากับ 10 ธุรกรรมต่อวินาที

ปริมาณนี้ไม่ถือว่าเป็น throughput ที่สูงสำหรับระบบฐานข้อมูลใด ๆ ดังนั้นจึงไม่ใช่จุดโฟกัสหลักของการสัมภาษณ์นี้

### **Pay-in flow**
นี่คือภาพรวมระดับสูงของ pay-in flow:

<div style="margin-left:3rem">
    <img src="./images/payin-flow-high-level.png" alt="pay-in-flow-high-level" width="500" />
</div>

 * Payment service - รับ payment event และประสานงาน (coordinate) กระบวนการชำระเงิน โดยทั่วไปยังทำการตรวจสอบความเสี่ยง (risk check) โดยใช้ผู้ให้บริการภายนอกเพื่อตรวจจับการละเมิดกฎ AML หรือกิจกรรมทางอาชญากรรม
 * Payment executor - ดำเนินการ payment order เดี่ยว ๆ ผ่าน Payment Service Provider (PSP) โดย payment event หนึ่งรายการอาจมี payment order หลายรายการ
 * Payment service provider (PSP) - เคลื่อนย้ายเงินจากบัญชีหนึ่งไปยังอีกบัญชีหนึ่ง เช่น จากบัญชีบัตรเครดิตของผู้ซื้อไปยังบัญชีธนาคารของเว็บไซต์ e-commerce
 * Card schemes - องค์กรที่ประมวลผล operation ของบัตรเครดิต เช่น Visa, MasterCard เป็นต้น
 * Ledger - เก็บบันทึกทางการเงินของธุรกรรมการชำระเงินทั้งหมด
 * Wallet - เก็บยอดคงเหลือในบัญชี (account balance) ของ merchant ทุกราย

นี่คือตัวอย่าง pay-in flow:
 * ผู้ใช้คลิก "place order" และ payment event จะถูกส่งไปยัง payment service
 * payment service จัดเก็บ event นั้นในฐานข้อมูลของตัวเอง
 * payment service เรียก payment executor สำหรับ payment order ทั้งหมดที่เป็นส่วนหนึ่งของ payment event นั้น
 * payment executor จัดเก็บ payment order ในฐานข้อมูลของตัวเอง
 * payment executor เรียก PSP ภายนอกเพื่อประมวลผลการชำระเงินด้วยบัตรเครดิต
 * หลังจาก payment executor ประมวลผลการชำระเงินเสร็จ payment service จะอัปเดต wallet เพื่อบันทึกว่าผู้ขายมีเงินเท่าไร
 * wallet service จัดเก็บข้อมูลยอดคงเหลือที่อัปเดตแล้วในฐานข้อมูลของตัวเอง
 * payment service เรียก ledger เพื่อบันทึกการเคลื่อนย้ายเงินทั้งหมด

### **API สำหรับ payment service**
```
POST /v1/payments
{
  "buyer_info": {...},
  "checkout_id": "some_id",
  "credit_card_info": {...},
  "payment_orders": [{...}, {...}, {...}]
}
```

ตัวอย่าง `payment_order`:
```
{
  "seller_account": "SELLER_IBAN",
  "amount": "3.15",
  "currency": "USD",
  "payment_order_id": "globally_unique_payment_id"
}
```

ข้อควรระวัง:
 * `payment_order_id` จะถูกส่งต่อไปยัง PSP เพื่อกำจัดข้อมูลซ้ำ (deduplicate) ของการชำระเงิน กล่าวคือมันเป็น idempotency key
 * field `amount` เป็นชนิด `string` เนื่องจาก `double` ไม่เหมาะสมสำหรับการแทนค่าทางการเงิน

```
GET /v1/payments/{:id}
```

endpoint นี้ส่งคืนสถานะการดำเนินการของการชำระเงินหนึ่งรายการ โดยอิงตาม `payment_order_id`

### **โมเดลข้อมูลของ payment service**
เราต้องดูแลรักษาสองตาราง - `payment_events` และ `payment_orders`

สำหรับการชำระเงิน ประสิทธิภาพ (performance) มักไม่ใช่ปัจจัยที่สำคัญ แต่ strong consistency นั้นสำคัญ

ข้อพิจารณาอื่น ๆ ในการเลือกฐานข้อมูล:
 * มีตลาดแรงงาน DBA ที่แข็งแกร่งให้จ้างมาดูแลฐานข้อมูล
 * มีประวัติที่ผ่านการพิสูจน์แล้ว (proven track-record) ว่าฐานข้อมูลนี้เคยถูกใช้โดยสถาบันการเงินขนาดใหญ่รายอื่น
 * ความหลากหลายของเครื่องมือสนับสนุน
 * เลือก SQL แบบดั้งเดิมมากกว่า NoSQL/NewSQL เนื่องจากการรับประกัน ACID

นี่คือสิ่งที่ตาราง `payment_events` มี:
 * `checkout_id` - string, primary key
 * `buyer_info` - string (หมายเหตุส่วนตัวของผู้เขียน - น่าจะเหมาะสมกว่าถ้าใช้ foreign key ไปยังอีกตาราง)
 * `seller_info` - string (หมายเหตุส่วนตัวของผู้เขียน - เช่นเดียวกับข้างต้น)
 * `credit_card_info` - ขึ้นอยู่กับผู้ให้บริการบัตร
 * `is_payment_done` - boolean

นี่คือสิ่งที่ตาราง `payment_orders` มี:
 * `payment_order_id` - string, primary key
 * `buyer_account` - string
 * `amount` - string
 * `currency` - string
 * `checkout_id` - string, foreign key
 * `payment_order_status` - enum (`NOT_STARTED`, `EXECUTING`, `SUCCESS`, `FAILED`)
 * `ledger_updated` - boolean
 * `wallet_updated` - boolean

ข้อควรระวัง:
 * มี payment order จำนวนมากที่เชื่อมโยงกับ payment event หนึ่งรายการ
 * เราไม่ต้องการ `seller_info` สำหรับ pay-in flow ข้อมูลนี้จำเป็นเฉพาะสำหรับ pay-out เท่านั้น
 * `ledger_updated` และ `wallet_updated` จะถูกอัปเดตเมื่อบริการที่เกี่ยวข้องถูกเรียกเพื่อบันทึกผลลัพธ์ของการชำระเงิน
 * การเปลี่ยนสถานะการชำระเงิน (payment transitions) ถูกจัดการโดย background job ซึ่งตรวจสอบการอัปเดตของการชำระเงินที่กำลังดำเนินการอยู่ (in-flight) และแจ้งเตือนหากการชำระเงินไม่ถูกประมวลผลภายในเวลาที่เหมาะสม

### **ระบบบัญชีแบบบันทึกคู่ (Double-entry ledger system)**
กลไกการทำบัญชีแบบบันทึกคู่ (double-entry accounting) เป็นหัวใจสำคัญของระบบชำระเงินใด ๆ มันเป็นกลไกที่ติดตามการเคลื่อนย้ายเงินโดยการนำ operation ทางการเงินไปใช้กับสองบัญชีเสมอ โดยบัญชีหนึ่งจะมียอดคงเหลือเพิ่มขึ้น (credit) และอีกบัญชีจะลดลง (debit):

| บัญชี (Account) | Debit | Credit |
|---------|-------|--------|
| ผู้ซื้อ (buyer)   | $1    |        |
| ผู้ขาย (seller)  |       | $1     |

ผลรวมของรายการธุรกรรมทั้งหมดจะเท่ากับศูนย์เสมอ กลไกนี้ช่วยให้สามารถตรวจสอบย้อนกลับ (traceability) ได้ตลอดสายการเคลื่อนย้ายเงินทั้งหมดภายในระบบ

## ขั้นตอนที่ 3: เจาะลึกการออกแบบ (Design Deep Dive)
หัวข้อนี้เน้นไปที่การทำให้ระบบเร็วขึ้น แข็งแกร่งขึ้น (robust) และปลอดภัยยิ่งขึ้น

### **การเชื่อมต่อกับ PSP (PSP Integration)**
หากระบบของเราสามารถเชื่อมต่อกับธนาคารหรือ card scheme ได้โดยตรง การชำระเงินก็สามารถทำได้โดยไม่ต้องผ่าน PSP
การเชื่อมต่อลักษณะนี้เกิดขึ้นได้ยากมากและไม่ค่อยพบเห็น โดยทั่วไปทำได้เฉพาะบริษัทขนาดใหญ่ที่สามารถให้เหตุผลรองรับการลงทุนนั้นได้

หากเราเลือกใช้เส้นทางแบบดั้งเดิม PSP สามารถถูก integrate ได้สองรูปแบบ:
 * ผ่าน API หากระบบชำระเงินของเราสามารถเก็บรวบรวมข้อมูลการชำระเงินได้
 * ผ่านหน้าชำระเงินแบบ hosted เพื่อหลีกเลี่ยงการต้องจัดการกับกฎระเบียบเกี่ยวกับข้อมูลการชำระเงิน

นี่คือวิธีที่ workflow ของหน้าชำระเงินแบบ hosted ทำงาน:

<div style="margin-left:3rem">
    <img src="./images/hosted-payment-page-workflow.png" alt="hosted-payment-page-workflow" width="500" />
</div>

 * ผู้ใช้คลิกปุ่ม "checkout" ในเบราว์เซอร์
 * ไคลเอนต์เรียก payment service พร้อมข้อมูล payment order
 * เมื่อได้รับข้อมูล payment order แล้ว payment service จะส่ง payment registration request ไปยัง PSP
 * PSP รับข้อมูลการชำระเงิน เช่น สกุลเงิน, จำนวนเงิน, วันหมดอายุ เป็นต้น รวมถึง UUID เพื่อวัตถุประสงค์ด้าน idempotency ซึ่งโดยทั่วไปคือ UUID ของ payment order
 * PSP ส่ง token กลับมา ซึ่งระบุการลงทะเบียนการชำระเงินนั้นอย่างไม่ซ้ำกัน token นี้จะถูกจัดเก็บไว้ในฐานข้อมูลของ payment service
 * เมื่อ token ถูกจัดเก็บแล้ว ผู้ใช้จะได้รับหน้าชำระเงินที่ hosted โดย PSP โดยหน้านั้นจะถูก initialize ด้วย token รวมถึง redirect URL สำหรับกรณีสำเร็จ/ล้มเหลว
 * ผู้ใช้กรอกรายละเอียดการชำระเงินในหน้า PSP, PSP ประมวลผลการชำระเงินและส่งคืนสถานะการชำระเงิน
 * ผู้ใช้จะถูก redirect กลับไปยัง redirectURL ตัวอย่าง redirect url - `https://your-company.com/?tokenID=JIOUIQ123NSF&payResult=X324FSa`
 * แบบอะซิงโครนัส (asynchronously) PSP จะเรียก payment service ของเราผ่าน webhook เพื่อแจ้ง backend ของเราถึงผลลัพธ์การชำระเงิน
 * payment service บันทึกผลลัพธ์การชำระเงินโดยอิงตาม webhook ที่ได้รับ

### **การกระทบยอด (Reconciliation)**
หัวข้อก่อนหน้าอธิบาย happy path ของการชำระเงิน ส่วน unhappy path จะถูกตรวจจับและกระทบยอดโดยใช้กระบวนการกระทบยอดที่ทำงานอยู่เบื้องหลัง (background reconciliation process)

ทุกคืน PSP จะส่ง settlement file ซึ่งระบบของเราใช้เพื่อเปรียบเทียบสถานะของระบบภายนอกกับสถานะของระบบภายในของเรา

<div style="margin-left:3rem">
    <img src="./images/settlement-report.png" alt="settlement-report" width="500" />
</div>

กระบวนการนี้ยังสามารถใช้ตรวจจับความไม่สอดคล้องภายใน เช่น ระหว่าง ledger service และ wallet service ได้ด้วย

ความไม่ตรงกัน (mismatch) จะถูกจัดการโดยทีมการเงินด้วยตนเอง โดยความไม่ตรงกันจะถูกจัดการดังนี้:
 * สามารถจัดหมวดหมู่ได้ (classifiable) จึงเป็นความไม่ตรงกันที่รู้จักแล้ว ซึ่งสามารถปรับแก้ได้ด้วยกระบวนการมาตรฐาน
 * สามารถจัดหมวดหมู่ได้ แต่ไม่สามารถทำอัตโนมัติได้ ต้องปรับแก้ด้วยมือโดยทีมการเงิน
 * ไม่สามารถจัดหมวดหมู่ได้ ต้องตรวจสอบและปรับแก้ด้วยมือโดยทีมการเงิน

### **การจัดการความล่าช้าในการประมวลผลการชำระเงิน (Handling payment processing delays)**
มีบางกรณีที่การชำระเงินอาจใช้เวลาหลายชั่วโมงกว่าจะเสร็จสมบูรณ์ แม้ว่าโดยทั่วไปจะใช้เวลาเพียงไม่กี่วินาที

สิ่งนี้อาจเกิดขึ้นได้เนื่องจาก:
 * การชำระเงินถูกตั้งค่าสถานะว่ามีความเสี่ยงสูง (high-risk) และจำเป็นต้องมีคนตรวจสอบด้วยตนเอง
 * บัตรเครดิตต้องการการป้องกันเพิ่มเติม เช่น 3D Secure Authentication ซึ่งต้องการรายละเอียดเพิ่มเติมจากเจ้าของบัตรเพื่อให้เสร็จสมบูรณ์

สถานการณ์เหล่านี้ถูกจัดการโดย:
 * รอให้ PSP ส่ง webhook มาแจ้งเราเมื่อการชำระเงินเสร็จสมบูรณ์ หรือ polling API ของ PSP หากไม่มี webhook ให้ใช้
 * แสดงสถานะ "pending" ให้ผู้ใช้เห็น และมอบหน้าเว็บที่ผู้ใช้สามารถกลับมาตรวจสอบความคืบหน้าของการชำระเงินได้ เรายังสามารถส่งอีเมลแจ้งเมื่อการชำระเงินเสร็จสมบูรณ์ได้ด้วย

### **การสื่อสารระหว่างบริการภายใน (Communication among internal services)**
มีรูปแบบการสื่อสารสองแบบที่บริการต่าง ๆ ใช้สื่อสารกัน - แบบซิงโครนัส (synchronous) และแบบอะซิงโครนัส (asynchronous)

การสื่อสารแบบซิงโครนัส (เช่น HTTP) ทำงานได้ดีสำหรับระบบขนาดเล็ก แต่จะมีปัญหาเมื่อขนาดระบบเพิ่มขึ้น:
 * ประสิทธิภาพต่ำ - รอบ request-response ยาวนานขึ้นเมื่อมีบริการเข้าร่วมในสาย call มากขึ้น
 * การแยกความล้มเหลว (failure isolation) ไม่ดี - หาก PSP หรือบริการอื่นล้มเหลว ผู้ใช้จะไม่ได้รับ response
 * การเชื่อมโยงกันแน่นเกินไป (tight coupling) - ผู้ส่งต้องรู้จักผู้รับ
 * ขยาย (scale) ได้ยาก - ไม่ง่ายที่จะรองรับทราฟฟิกที่เพิ่มขึ้นอย่างฉับพลัน เนื่องจากไม่มีบัฟเฟอร์

การสื่อสารแบบอะซิงโครนัสสามารถแบ่งได้เป็นสองประเภท

ผู้รับรายเดียว (Single receiver) - ผู้รับหลายรายสมัครสมาชิก (subscribe) topic เดียวกัน แต่แต่ละข้อความจะถูกประมวลผลเพียงครั้งเดียว:

</div>

ผู้รับหลายราย (Multiple receivers) - ผู้รับหลายรายสมัครสมาชิก topic เดียวกัน แต่ข้อความจะถูกส่งต่อไปยังทุกคน:

<div style="margin-left:3rem">

โมเดลหลังนี้เหมาะกับระบบชำระเงินของเรา เนื่องจากการชำระเงินหนึ่งครั้งสามารถกระตุ้นผลข้างเคียง (side effect) หลายอย่าง ซึ่งจัดการโดยบริการที่แตกต่างกัน

โดยสรุปแล้ว การสื่อสารแบบซิงโครนัสนั้นง่ายกว่า แต่ไม่ทำให้บริการมีความเป็นอิสระ (autonomous)
การสื่อสารแบบอะซิงโครนัสแลกความเรียบง่ายและความสอดคล้องของข้อมูล เพื่อให้ได้ความสามารถในการขยายและความยืดหยุ่นต่อความล้มเหลว (resilience)

### **การจัดการการชำระเงินที่ล้มเหลว (Handling failed payments)**
ระบบชำระเงินทุกระบบต้องจัดการกับการชำระเงินที่ล้มเหลว นี่คือกลไกบางส่วนที่เราจะใช้เพื่อบรรลุเป้าหมายนั้น:
 * การติดตามสถานะการชำระเงิน - เมื่อใดก็ตามที่การชำระเงินล้มเหลว เราสามารถตัดสินใจว่าจะลองใหม่ (retry) หรือคืนเงิน (refund) โดยอิงตามสถานะของการชำระเงิน
 * Retry queue - การชำระเงินที่เราจะลองใหม่จะถูกส่งไปยัง retry queue
 * Dead-letter queue - การชำระเงินที่ล้มเหลวอย่างสิ้นเชิงจะถูกส่งไปยัง dead-letter queue ซึ่งการชำระเงินที่ล้มเหลวสามารถถูกดีบักและตรวจสอบได้

### **การส่งข้อมูลแบบ exactly-once (Exactly-once delivery)**
เราต้องมั่นใจว่าการชำระเงินถูกประมวลผลเพียงครั้งเดียวเท่านั้น (exactly-once) เพื่อหลีกเลี่ยงการเรียกเก็บเงินซ้ำจากลูกค้า

operation หนึ่งจะถูกดำเนินการแบบ exactly-once ก็ต่อเมื่อมันถูกดำเนินการอย่างน้อยหนึ่งครั้ง (at-least-once) และไม่เกินหนึ่งครั้ง (at-most-once) ในเวลาเดียวกัน

เพื่อให้ได้การรับประกัน at-least-once เราจะใช้กลไกการลองใหม่ (retry mechanism):

<div style="margin-left:3rem">
    <img src="./images/retry-mechanism.png" alt="retry-mechanism" width="500" />
</div>

นี่คือกลยุทธ์ทั่วไปในการตัดสินใจเลือกช่วงเวลาในการ retry:
 * immediate retry - ไคลเอนต์ส่ง request อีกครั้งทันทีหลังจากล้มเหลว
 * fixed intervals - รอเป็นระยะเวลาคงที่ก่อนที่จะลองการชำระเงินใหม่
 * incremental intervals - เพิ่มช่วงเวลา retry ขึ้นทีละน้อยระหว่างการ retry แต่ละครั้ง
 * exponential back-off - เพิ่มช่วงเวลา retry เป็นสองเท่าในการ retry ครั้งถัดไป
 * cancel - ไคลเอนต์ยกเลิก request ซึ่งจะเกิดขึ้นเมื่อ error นั้นเป็นแบบถาวร (terminal) หรือถึงเกณฑ์การ retry สูงสุดแล้ว

ตามหลักทั่วไป ควรใช้กลยุทธ์ exponential back-off retry เป็นค่าเริ่มต้น แนวปฏิบัติที่ดีคือให้เซิร์ฟเวอร์ระบุช่วงเวลาการ retry ผ่าน header `Retry-After`

ปัญหาหนึ่งของการ retry คือเซิร์ฟเวอร์อาจประมวลผลการชำระเงินซ้ำสองครั้งได้:
 * ไคลเอนต์คลิกปุ่ม "pay" สองครั้ง ส่งผลให้ถูกเรียกเก็บเงินสองครั้ง
 * การชำระเงินถูกประมวลผลสำเร็จโดย PSP แต่ไม่สำเร็จในบริการปลายทาง (ledger, wallet) การ retry ทำให้ PSP ประมวลผลการชำระเงินอีกครั้ง

เพื่อแก้ปัญหาการชำระเงินซ้ำนี้ เราจำเป็นต้องใช้กลไก idempotency - คุณสมบัติที่ operation หนึ่งถูกเรียกใช้หลายครั้ง แต่ถูกประมวลผลเพียงครั้งเดียวเท่านั้น

จากมุมมองของ API ไคลเอนต์สามารถเรียก call หลายครั้งซึ่งให้ผลลัพธ์เดียวกันได้
idempotency ถูกจัดการโดย header พิเศษใน request (เช่น `idempotency-key`) ซึ่งโดยทั่วไปคือ UUID

<div style="margin-left:3rem">
    <img src="./images/idempotency-example.png" alt="idempotency-example" width="500" />
</div>

idempotency สามารถบรรลุได้โดยใช้กลไกของฐานข้อมูลในการเพิ่ม unique key constraint:
 * เซิร์ฟเวอร์พยายามแทรก row ใหม่ลงในฐานข้อมูล
 * การแทรกล้มเหลวเนื่องจากละเมิด unique key constraint
 * เซิร์ฟเวอร์ตรวจจับ error นั้น และส่งคืน object ที่มีอยู่แล้วกลับไปยังไคลเอนต์แทน

idempotency ยังถูกนำไปใช้ที่ฝั่ง PSP ด้วย โดยใช้ nonce ซึ่งได้กล่าวถึงไปก่อนหน้านี้ PSP จะดูแลไม่ให้ประมวลผลการชำระเงินที่มี nonce เดียวกันซ้ำสองครั้ง

### **ความสอดคล้องของข้อมูล (Consistency)**
มีบริการแบบ stateful หลายตัวที่ถูกเรียกใช้ตลอดวงจรชีวิต (lifecycle) ของการชำระเงิน - PSP, ledger, wallet, payment service

การสื่อสารระหว่างสองบริการใด ๆ สามารถล้มเหลวได้
เราสามารถรับประกันความสอดคล้องของข้อมูลแบบ eventual consistency ระหว่างบริการทั้งหมดได้ ด้วยการ implement การประมวลผลแบบ exactly-once และการกระทบยอด (reconciliation)

หากเราใช้ replication เราจะต้องจัดการกับ replication lag ซึ่งอาจทำให้ผู้ใช้เห็นข้อมูลที่ไม่สอดคล้องกันระหว่างฐานข้อมูล primary และ replica

เพื่อลดผลกระทบนี้ เราสามารถให้บริการทั้งการอ่านและการเขียนจากฐานข้อมูล primary เท่านั้น และใช้ replica เพื่อความซ้ำซ้อน (redundancy) และการ fail-over เท่านั้น
อีกทางเลือกหนึ่ง เราสามารถมั่นใจได้ว่า replica ซิงค์กันอยู่เสมอ โดยใช้ consensus algorithm อย่าง Paxos หรือ Raft
เรายังสามารถใช้ฐานข้อมูลแบบ distributed ที่อิง consensus เช่น YugabyteDB หรือ CockroachDB ได้เช่นกัน

### **ความปลอดภัยของการชำระเงิน (Payment security)**
นี่คือกลไกบางส่วนที่เราสามารถใช้เพื่อรับประกันความปลอดภัยของการชำระเงิน:
 * การดักฟัง request/response - เราสามารถใช้ HTTPS เพื่อรักษาความปลอดภัยของการสื่อสารทั้งหมด
 * การปลอมแปลงข้อมูล (Data tampering) - บังคับใช้การเข้ารหัส (encryption) และการตรวจสอบความสมบูรณ์ (integrity monitoring)
 * การโจมตีแบบ Man-in-the-middle - ใช้ SSL ร่วมกับ certificate pinning
 * การสูญเสียข้อมูล (Data loss) - ทำสำเนาข้อมูลไปยังหลายภูมิภาคและถ่าย snapshot ของข้อมูล
 * การโจมตีแบบ DDoS - implement rate limiting และ firewall
 * การขโมยข้อมูลบัตร (Card theft) - ใช้ token แทนการจัดเก็บข้อมูลบัตรจริงในระบบของเรา
 * การปฏิบัติตามมาตรฐาน PCI (PCI compliance) - มาตรฐานความปลอดภัยสำหรับองค์กรที่จัดการบัตรเครดิตแบรนด์ต่าง ๆ
 * การฉ้อโกง (Fraud) - การตรวจสอบที่อยู่ (address verification), รหัสยืนยันบัตร (card verification value - CVV), การวิเคราะห์พฤติกรรมผู้ใช้ เป็นต้น

 * เครื่องมือดีบัก (Debugging tools) - เราต้องการเครื่องมือที่ทำให้เข้าใจได้ง่ายว่าทำไมการชำระเงินถึงล้มเหลว
