# บทที่ 21: การรวบรวมข้อมูลเหตุการณ์การคลิกโฆษณา (Ad Click Event Aggregation)

## บทนำ
**การโฆษณาดิจิทัล (Digital advertising)** เป็นอุตสาหกรรมขนาดใหญ่ที่เติบโตขึ้นมาพร้อมกับการเติบโตของ Facebook, YouTube, TikTok และอื่น ๆ

ดังนั้น การติดตามเหตุการณ์การคลิกโฆษณา (ad click events) จึงมีความสำคัญ ในบทนี้ เราจะสำรวจวิธีการออกแบบระบบ **การรวบรวมข้อมูลเหตุการณ์การคลิกโฆษณา (ad click event aggregation)** ในระดับสเกลของ Facebook/Google

การโฆษณาดิจิทัลมีกระบวนการหนึ่งที่เรียกว่า **การประมูลแบบเรียลไทม์ (real-time bidding หรือ RTB)** ซึ่งเป็นกระบวนการที่พื้นที่โฆษณาดิจิทัล (digital advertising inventory) ถูกซื้อและขาย:

<div style="margin-left:3rem">
    <img src="./images/digital-advertising-example.png" alt="digital-advertising-example" width="500" />
</div>

ความเร็วของ RTB มีความสำคัญมาก เนื่องจากมักเกิดขึ้นภายในเวลาไม่ถึงหนึ่งวินาที
ความถูกต้องของข้อมูล (data accuracy) ก็มีความสำคัญมากเช่นกัน เนื่องจากส่งผลต่อจำนวนเงินที่ผู้ลงโฆษณา (advertisers) ต้องจ่าย

จากผลลัพธ์ของการรวบรวมข้อมูลการคลิกโฆษณา ผู้ลงโฆษณาสามารถนำไปใช้ในการตัดสินใจ เช่น การปรับกลุ่มเป้าหมาย (target audience) และคำสำคัญ (keywords)

## หัวข้อที่ 1: ทำความเข้าใจปัญหาและกำหนดขอบเขตการออกแบบ (Understand the Problem and Establish Design Scope)
 - C: รูปแบบของข้อมูลอินพุตเป็นอย่างไร?
 - I: มีการคลิกโฆษณา 1 พันล้านครั้งต่อวัน และมีโฆษณาทั้งหมด 2 ล้านชิ้น จำนวนเหตุการณ์การคลิกโฆษณาเติบโตขึ้น 30% ต่อปี (year-over-year)
 - C: query ที่สำคัญที่สุดที่ระบบของเราจำเป็นต้องรองรับมีอะไรบ้าง?
 - I: query หลักที่ต้องพิจารณา ได้แก่:
   - คืนค่าจำนวนเหตุการณ์การคลิกของโฆษณา X ใน Y นาทีที่ผ่านมา
   - คืนค่าโฆษณา 100 อันดับแรกที่ถูกคลิกมากที่สุดใน 1 นาทีที่ผ่านมา พารามิเตอร์ทั้งสองควรกำหนดค่าได้ (configurable) การรวบรวมข้อมูล (aggregation) เกิดขึ้นทุกนาที
   - รองรับการกรองข้อมูล (data filtering) ด้วย `ip`, `user_id`, `country` สำหรับ query ข้างต้น
 - C: เราจำเป็นต้องกังวลเกี่ยวกับกรณีขอบ (edge cases) หรือไม่? บางกรณีที่นึกออกมีดังนี้:
   - อาจมีเหตุการณ์ที่มาถึงล่าช้ากว่าที่คาดไว้
   - อาจมีเหตุการณ์ที่ซ้ำกัน (duplicate events)
   - บางส่วนของระบบอาจล่ม จึงจำเป็นต้องพิจารณาเรื่องการกู้คืนระบบ (system recovery)
 - I: นั่นเป็นรายการที่ดี ให้นำสิ่งเหล่านั้นมาพิจารณาด้วย
 - C: ข้อกำหนดด้าน latency เป็นอย่างไร?
 - I: latency แบบ end-to-end (e2e) สำหรับการรวบรวมข้อมูลการคลิกโฆษณาอยู่ที่ไม่กี่นาที สำหรับ RTB จะต้องน้อยกว่าหนึ่งวินาที การมี latency ระดับนั้นสำหรับการรวบรวมข้อมูลการคลิกโฆษณาถือว่ายอมรับได้ เนื่องจากมักถูกใช้เพื่อการเรียกเก็บเงิน (billing) และการรายงาน (reporting)

### **ความต้องการเชิงฟังก์ชัน (Functional requirements)**
 - รวบรวมจำนวนการคลิกของ `ad_id` ใน Y นาทีที่ผ่านมา
 - คืนค่า `ad_id` ที่ถูกคลิกมากที่สุด 100 อันดับแรกทุกนาที
 - รองรับการกรองข้อมูลการรวบรวม (aggregation filtering) ด้วยแอตทริบิวต์ (attributes) ที่แตกต่างกัน
 - ปริมาณข้อมูลอยู่ในระดับสเกลของ Facebook หรือ Google

### **ความต้องการที่ไม่ใช่เชิงฟังก์ชัน (Non-functional requirements)**
 - ความถูกต้อง (correctness) ของผลลัพธ์การรวบรวมข้อมูลมีความสำคัญ เนื่องจากถูกใช้สำหรับ RTB และการเรียกเก็บเงินค่าโฆษณา
 - จัดการกับเหตุการณ์ที่ล่าช้าหรือซ้ำกันได้อย่างเหมาะสม
 - ความทนทาน (Robustness) - ระบบควรมีความยืดหยุ่นต่อความล้มเหลวบางส่วน (partial failures)
 - Latency - e2e latency ไม่เกินสองสามนาที

### **การประมาณการคร่าว ๆ (Back-of-the-envelope estimation)**
 - ผู้ใช้งานประจำวัน (DAU) 1 พันล้านคน
 - สมมติว่าผู้ใช้คลิกโฆษณา 1 ครั้งต่อวัน -> การคลิกโฆษณา 1 พันล้านครั้งต่อวัน
 - QPS ของการคลิกโฆษณา = 10,000
 - Peak QPS เป็น 5 เท่าของจำนวนนั้น = 50,000
 - การคลิกโฆษณาหนึ่งครั้งใช้พื้นที่จัดเก็บ 0.1KB ความต้องการพื้นที่จัดเก็บต่อวันคือ 100gb
 - พื้นที่จัดเก็บต่อเดือน = 3tb

## หัวข้อที่ 2: นำเสนอการออกแบบระดับสูงและขอความเห็นชอบ (Propose High-Level Design and Get Buy-In)
ในส่วนนี้ เราจะพูดถึงการออกแบบ query API, data model และการออกแบบระดับสูง (high-level design)

### **การออกแบบ Query API (Query API Design)**
API คือสัญญา (contract) ระหว่างไคลเอนต์และเซิร์ฟเวอร์ ในกรณีของเรา ไคลเอนต์คือผู้ใช้แดชบอร์ด (dashboard user) เช่น นักวิทยาศาสตร์ข้อมูล/นักวิเคราะห์ (data scientist/analyst), ผู้ลงโฆษณา เป็นต้น

นี่คือความต้องการเชิงฟังก์ชันของเรา:
 - รวบรวมจำนวนการคลิกของ `ad_id` ใน Y นาทีที่ผ่านมา
 - คืนค่า `ad_id` ที่ถูกคลิกมากที่สุด N อันดับแรกใน M นาทีที่ผ่านมา
 - รองรับการกรองข้อมูลการรวบรวมด้วยแอตทริบิวต์ที่แตกต่างกัน

เราต้องการ endpoint สองตัวเพื่อให้บรรลุความต้องการเหล่านั้น การกรองข้อมูลสามารถทำได้ผ่าน query parameters บน endpoint ตัวใดตัวหนึ่ง

**รวบรวมจำนวนการคลิกของ ad_id ใน M นาทีที่ผ่านมา**:

```
GET /v1/ads/{:ad_id}/aggregated_count
```

Query parameters:
 - from - นาทีเริ่มต้น ค่าเริ่มต้นคือ ตอนนี้ลบไป 1 นาที
 - to - นาทีสิ้นสุด ค่าเริ่มต้นคือ ตอนนี้
 - filter - identifier สำหรับกลยุทธ์การกรองที่แตกต่างกัน เช่น 001 หมายถึง "การคลิกที่ไม่ใช่จากสหรัฐฯ"

Response:
 - ad_id - ตัวระบุโฆษณา
 - count - จำนวนที่ถูกรวบรวมระหว่างนาทีเริ่มต้นและนาทีสิ้นสุด

**คืนค่า ad_id ที่ถูกคลิกมากที่สุด N อันดับแรกใน M นาทีที่ผ่านมา**

```
GET /v1/ads/popular_ads
```

Query parameters:
 - count - โฆษณาที่ถูกคลิกมากที่สุด N อันดับแรก
 - window - ขนาดของหน้าต่างการรวบรวมข้อมูล (aggregation window) เป็นนาที
 - filter - identifier สำหรับกลยุทธ์การกรองที่แตกต่างกัน

Response:
 - รายการของ ad_id

### **Data model**
ในระบบของเรา เรามีข้อมูลดิบ (raw data) และข้อมูลที่ถูกรวบรวมแล้ว (aggregated data)

ข้อมูลดิบมีลักษณะดังนี้:

```
[AdClickEvent] ad001, 2021-01-01 00:00:01, user 1, 207.148.22.22, USA
```

นี่คือตัวอย่างในรูปแบบที่มีโครงสร้าง:
| ad_id | click_timestamp     | user  | ip            | country |
|-------|---------------------|-------|---------------|---------|
| ad001 | 2021-01-01 00:00:01 | user1 | 207.148.22.22 | USA     |
| ad001 | 2021-01-01 00:00:02 | user1 | 207.148.22.22 | USA     |
| ad002 | 2021-01-01 00:00:02 | user2 | 209.153.56.11 | USA     |

นี่คือเวอร์ชันที่ถูกรวบรวมแล้ว:
| ad_id | click_minute | filter_id | count |
|-------|--------------|-----------|-------|
| ad001 | 202101010000 | 0012      | 2     |
| ad001 | 202101010000 | 0023      | 3     |
| ad001 | 202101010001 | 0012      | 1     |
| ad001 | 202101010001 | 0023      | 6     |

`filter_id` ช่วยให้เราบรรลุความต้องการด้านการกรองข้อมูลของเรา
| filter_id | region | IP        | user_id |
|-----------|--------|-----------|---------|
| 0012      | US     | *         | *       |
| 0013      | *      | 123.1.2.3 | *       |

เพื่อรองรับการคืนค่าโฆษณาที่ถูกคลิกมากที่สุด N อันดับแรกในช่วง M นาทีที่ผ่านมาอย่างรวดเร็ว เราจะดูแลรักษาโครงสร้างนี้ด้วยเช่นกัน:
| most_clicked_ads   |           |                                                  |
|--------------------|-----------|--------------------------------------------------|
| window_size        | integer   | ขนาดของหน้าต่างการรวบรวมข้อมูล (M) เป็นนาที       |
| update_time_minute | timestamp | เวลาที่อัปเดตล่าสุด (ความละเอียดระดับ 1 นาที) |
| most_clicked_ads   | array     | รายการ ad ID ในรูปแบบ JSON                   |

ข้อดีและข้อเสียระหว่างการจัดเก็บข้อมูลดิบและการจัดเก็บข้อมูลที่ถูกรวบรวมแล้วมีอะไรบ้าง?
 - ข้อมูลดิบช่วยให้สามารถใช้ชุดข้อมูลทั้งหมดได้ และรองรับการกรองข้อมูลรวมถึงการคำนวณใหม่ (recalculation)
 - ในทางกลับกัน ข้อมูลที่ถูกรวบรวมแล้วทำให้เรามีชุดข้อมูลขนาดเล็กลงและ query ที่เร็วขึ้น
 - ข้อมูลดิบหมายถึงการมี data store ที่ใหญ่กว่าและ query ที่ช้ากว่า
 - อย่างไรก็ตาม ข้อมูลที่ถูกรวบรวมแล้วเป็นข้อมูลที่ได้มาจากการประมวลผล (derived data) จึงมีการสูญเสียข้อมูลบางส่วน

ในการออกแบบของเรา เราจะใช้ทั้งสองวิธีร่วมกัน:
 - เป็นความคิดที่ดีที่จะเก็บข้อมูลดิบไว้เพื่อการดีบัก (debugging) หากมีบั๊กในการรวบรวมข้อมูล เราสามารถค้นพบบั๊กนั้นและทำการ backfill ได้
 - ข้อมูลที่ถูกรวบรวมแล้วควรถูกจัดเก็บไว้ด้วยเช่นกัน เพื่อประสิทธิภาพการ query ที่เร็วขึ้น
 - ข้อมูลดิบสามารถจัดเก็บไว้ใน cold storage เพื่อหลีกเลี่ยงค่าใช้จ่ายในการจัดเก็บที่เพิ่มขึ้น

เมื่อพูดถึงฐานข้อมูล มีปัจจัยหลายอย่างที่ต้องนำมาพิจารณา:
 - ข้อมูลมีลักษณะอย่างไร? เป็นแบบ relational, document หรือ blob?
 - workload เน้นการอ่านหนัก (read-heavy), การเขียนหนัก (write-heavy) หรือทั้งสองอย่าง?
 - จำเป็นต้องมี transaction หรือไม่?
 - query ต้องพึ่งพาฟังก์ชัน OLAP อย่าง SUM และ COUNT หรือไม่?

สำหรับข้อมูลดิบ เราจะเห็นว่า QPS เฉลี่ยอยู่ที่ 10k และ peak QPS อยู่ที่ 50k ดังนั้นระบบจึงเป็นแบบ write-heavy
ในทางกลับกัน read traffic นั้นต่ำ เนื่องจากข้อมูลดิบส่วนใหญ่ถูกใช้เป็นข้อมูลสำรอง (backup) ในกรณีที่มีอะไรผิดพลาด

ฐานข้อมูลเชิงสัมพันธ์ (Relational databases) สามารถทำงานนี้ได้ แต่การขยาย (scale) การเขียนอาจเป็นเรื่องท้าทาย
อีกทางเลือกหนึ่งคือใช้ Cassandra หรือ InfluxDB ซึ่งมีการรองรับ workload การเขียนหนักในตัวได้ดีกว่า

อีกตัวเลือกหนึ่งคือใช้ Amazon S3 ร่วมกับรูปแบบข้อมูลแบบคอลัมน์ (columnar data format) เช่น ORC, Parquet หรือ AVRO เนื่องจากการตั้งค่านี้ไม่คุ้นเคย เราจะเลือกใช้ Cassandra

สำหรับข้อมูลที่ถูกรวบรวมแล้ว workload มีทั้งการอ่านและการเขียนที่หนัก เนื่องจากข้อมูลที่ถูกรวบรวมแล้วถูก query อย่างต่อเนื่องสำหรับแดชบอร์ดและการแจ้งเตือน (alerts)
มันยังเป็น write-heavy ด้วย เนื่องจากข้อมูลถูกรวบรวมและเขียนทุกนาทีโดย aggregation service
ดังนั้นเราจะใช้ data store เดียวกัน (Cassandra) ในส่วนนี้ด้วยเช่นกัน

### **Streaming เทียบกับ Batching (Streaming vs. Batching)**
สถาปัตยกรรมระดับสูงที่เรานำเสนอเป็นระบบประมวลผลแบบสตรีม (stream processing) ประเภทหนึ่ง
นี่คือการเปรียบเทียบระหว่างระบบสามประเภท:
|                         | Services (ระบบออนไลน์)      | ระบบแบบ Batch (ระบบออฟไลน์)                          | ระบบแบบ Streaming (ระบบใกล้เรียลไทม์)     |
|-------------------------|-------------------------------|--------------------------------------------------------|----------------------------------------------|
| การตอบสนอง (Responsiveness)          | ตอบสนองต่อไคลเอนต์อย่างรวดเร็ว | ไม่จำเป็นต้องตอบสนองต่อไคลเอนต์                       | ไม่จำเป็นต้องตอบสนองต่อไคลเอนต์             |
| อินพุต (Input)                   | คำขอจากผู้ใช้ (User requests)                 | อินพุตแบบมีขอบเขต (bounded) ที่มีขนาดจำกัด ปริมาณข้อมูลมาก | อินพุตไม่มีขอบเขต (สตรีมแบบไม่จำกัด)     |
| เอาต์พุต (Output)                  | คำตอบส่งกลับไปยังไคลเอนต์                | materialized view, ตัวชี้วัดที่ถูกรวบรวม เป็นต้น           | materialized view, ตัวชี้วัดที่ถูกรวบรวม เป็นต้น |
| การวัดประสิทธิภาพ (Performance measurement) | ความพร้อมใช้งาน (Availability), latency         | Throughput                                             | Throughput, latency                          |
| ตัวอย่าง (Example)                 | การช้อปปิ้งออนไลน์               | MapReduce                                              | Flink [13]                                   |

ในการออกแบบของเรา เราใช้ทั้ง batching และ streaming ผสมผสานกัน

เราใช้ streaming สำหรับการประมวลผลข้อมูลขณะที่มันมาถึง และสร้างผลลัพธ์ที่ถูกรวบรวมแล้วในลักษณะใกล้เรียลไทม์ (near real-time)
ในทางกลับกัน เราใช้ batching สำหรับการสำรองข้อมูลย้อนหลัง (historical data backup)

ระบบที่มีเส้นทางการประมวลผลสองเส้นทาง - batch และ streaming - พร้อมกัน สถาปัตยกรรมนี้เรียกว่า lambda
ข้อเสียคือคุณจะต้องดูแลรักษาเส้นทางการประมวลผลสองเส้นทางที่มี codebase แตกต่างกันสองชุด

Kappa เป็นสถาปัตยกรรมทางเลือก ซึ่งรวม batch และ stream processing เข้าไว้ในเส้นทางการประมวลผลเดียว
แนวคิดหลักคือการใช้ stream processing engine เพียงตัวเดียว

### **เวลา (Time)**
เราจำเป็นต้องมี timestamp เพื่อทำการรวบรวมข้อมูล ซึ่งสามารถถูกสร้างขึ้นได้ในสองที่:
 - event time - เวลาที่การคลิกโฆษณาเกิดขึ้น
 - Processing time - เวลาของระบบเมื่อเซิร์ฟเวอร์ประมวลผลเหตุการณ์นั้น

เนื่องจากการใช้ async processing (message queue) และความล่าช้าของเครือข่าย (network delays) อาจมีความแตกต่างอย่างมีนัยสำคัญระหว่าง event time และ processing time
 - หากเราใช้ processing time ผลลัพธ์การรวบรวมข้อมูลอาจไม่ถูกต้อง
 - หากเราใช้ event time เราจะต้องจัดการกับเหตุการณ์ที่ล่าช้า

ไม่มีวิธีแก้ไขที่สมบูรณ์แบบ เราจำเป็นต้องพิจารณา trade-off:
|                 | ข้อดี                                  | ข้อเสีย                                                                                 |
|-----------------|---------------------------------------|--------------------------------------------------------------------------------------|
| Event time      | ผลลัพธ์การรวบรวมข้อมูลถูกต้องแม่นยำกว่า | ไคลเอนต์อาจมีเวลาที่ผิดพลาด หรือ timestamp อาจถูกสร้างขึ้นโดยผู้ใช้ที่มีเจตนาร้าย |
| Processing time | timestamp ของเซิร์ฟเวอร์น่าเชื่อถือกว่า     | timestamp ไม่ถูกต้องหากเหตุการณ์มาถึงล่าช้า                                       |

เนื่องจากความถูกต้องของข้อมูลมีความสำคัญ เราจะใช้ event time สำหรับการรวบรวมข้อมูล

เพื่อบรรเทาปัญหาเหตุการณ์ที่ล่าช้า สามารถใช้เทคนิคที่เรียกว่า "watermark" ได้

ในตัวอย่างด้านล่าง เหตุการณ์ที่ 2 พลาดหน้าต่าง (window) ที่มันควรจะถูกรวบรวม:

### **การรับประกันการส่งข้อมูล (Delivery guarantees)**
เนื่องจากข้อมูลที่เรากำลังรวบรวมจะถูกนำไปใช้ในการเรียกเก็บเงิน (billing) ความถูกต้องของข้อมูลจึงเป็นสิ่งสำคัญอันดับต้น ๆ

ดังนั้น เราจำเป็นต้องพูดถึง:
 - วิธีหลีกเลี่ยงการประมวลผลเหตุการณ์ที่ซ้ำกัน
 - วิธีตรวจสอบให้แน่ใจว่าเหตุการณ์ทั้งหมดถูกประมวลผล

มีการรับประกันการส่งข้อมูลสามแบบที่เราสามารถใช้ได้ - at-most-once, at-least-once และ exactly once

ในกรณีส่วนใหญ่ at-least-once ก็เพียงพอแล้ว เมื่อสามารถยอมรับข้อมูลซ้ำจำนวนเล็กน้อยได้
แต่กรณีนี้ไม่เป็นเช่นนั้นสำหรับระบบของเรา เนื่องจากความแตกต่างเพียงเล็กน้อยเป็นเปอร์เซ็นต์อาจส่งผลให้เกิดความคลาดเคลื่อนหลายล้านดอลลาร์
ดังนั้นเราจึงจำเป็นต้องใช้ semantics แบบ exactly-once delivery

### **การกำจัดข้อมูลซ้ำ (Data deduplication)**
หนึ่งในปัญหาคุณภาพข้อมูลที่พบบ่อยที่สุดคือข้อมูลที่ซ้ำกัน

มันสามารถมาจากแหล่งที่มาที่หลากหลาย:
 - ฝั่งไคลเอนต์ (Client-side) - ไคลเอนต์อาจส่งเหตุการณ์เดียวกันซ้ำหลายครั้ง เหตุการณ์ที่ซ้ำกันซึ่งถูกส่งด้วยเจตนาร้ายควรได้รับการจัดการโดย risk engine
 - เซิร์ฟเวอร์ขัดข้อง (Server outage) - aggregation service node ล่มระหว่างการรวบรวมข้อมูล และบริการต้นทาง (upstream) ยังไม่ได้รับการยืนยัน (acknowledgment) จึงมีการส่งเหตุการณ์ซ้ำอีกครั้ง

### **การขยายระบบ (Scale the system)**
มาพูดถึงวิธีที่เราขยายระบบเมื่อมันเติบโตขึ้น

เรามีคอมโพเนนต์อิสระสามส่วน - message queue, aggregation service และฐานข้อมูล
เนื่องจากทั้งสามถูกแยก (decoupled) ออกจากกัน เราจึงสามารถขยายแต่ละส่วนได้อย่างอิสระ

เราจะขยาย message queue อย่างไร:
 - เราไม่ได้จำกัดจำนวน producer ดังนั้นจึงสามารถขยายได้ง่าย
 - Consumer สามารถขยายได้โดยการกำหนดให้อยู่ใน consumer group และเพิ่มจำนวน consumer
 - เพื่อให้สิ่งนี้ทำงานได้ เรายังจำเป็นต้องตรวจสอบให้แน่ใจว่ามีการสร้าง partition ไว้เพียงพอล่วงหน้า
 - นอกจากนี้ การทำ consumer rebalancing อาจใช้เวลานานเมื่อมี consumer หลายพันตัว จึงแนะนำให้ทำในช่วงเวลาที่ไม่ใช่ peak hour
 - เรายังอาจพิจารณาการแบ่ง partition ของ topic ตามพื้นที่ทางภูมิศาสตร์ (geography) เช่น `topic_na`, `topic_eu` เป็นต้น

### **ความทนทานต่อความล้มเหลว (Fault Tolerance)**
ภายใน aggregation node เรากำลังประมวลผลข้อมูลแบบ in-memory หาก node ล่ม ข้อมูลที่ถูกประมวลผลจะสูญหาย

เราสามารถใช้ประโยชน์จาก consumer offset ใน Kafka เพื่อดำเนินการต่อจากจุดที่เราหยุดไว้ เมื่อ node ตัวอื่นเข้ามารับช่วงงานต่อ
อย่างไรก็ตาม ยังมี state ระดับกลาง (intermediary state) เพิ่มเติมที่เราต้องดูแลรักษา เนื่องจากเรากำลังรวบรวมโฆษณาที่ถูกคลิกมากที่สุด N อันดับแรกใน M นาที

เราสามารถสร้าง snapshot ณ นาทีใดนาทีหนึ่งสำหรับการรวบรวมข้อมูลที่กำลังดำเนินอยู่ (on-going):

### **การเฝ้าติดตามและความถูกต้องของข้อมูล (Data monitoring and correctness)**
เนื่องจากข้อมูลที่เรากำลังรวบรวมนั้นมีความสำคัญมาก เนื่องจากถูกใช้สำหรับการเรียกเก็บเงิน จึงสำคัญมากที่จะต้องมีการเฝ้าติดตาม (monitoring) ที่เข้มงวดเพื่อให้มั่นใจในความถูกต้อง

ตัวชี้วัด (metrics) บางอย่างที่เราอาจต้องการเฝ้าติดตาม:
 - **Latency**: สามารถติดตาม timestamp ของเหตุการณ์ต่าง ๆ เพื่อทำความเข้าใจ e2e latency ของระบบ
 - **ขนาดของ message queue**: หากมีการเพิ่มขึ้นอย่างฉับพลันของขนาด queue เราจำเป็นต้องเพิ่ม aggregation node เนื่องจาก Kafka ถูก implement ผ่าน distributed commit log เราจึงจำเป็นต้องติดตามตัวชี้วัด records-lag แทน
 - **ทรัพยากรระบบบน aggregation node**: CPU, disk, JVM เป็นต้น

เรายังจำเป็นต้อง implement กระบวนการกระทบยอด (reconciliation flow) ซึ่งเป็นงานแบบ batch ที่รันในช่วงสิ้นวัน
มันคำนวณผลลัพธ์ที่ถูกรวบรวมแล้วจากข้อมูลดิบ และเปรียบเทียบกับข้อมูลจริงที่จัดเก็บอยู่ใน aggregation database:

### **การออกแบบทางเลือก (Alternative design)**
ในการสัมภาษณ์ system design แบบทั่วไป คุณไม่จำเป็นต้องรู้รายละเอียดภายในของซอฟต์แวร์เฉพาะทางที่ใช้ในการประมวลผล big data

การอธิบายกระบวนการคิดและการพูดคุยเรื่อง trade-off มีความสำคัญมากกว่าการรู้จักเครื่องมือเฉพาะเจาะจง ซึ่งเป็นเหตุผลที่บทนี้ครอบคลุมวิธีแก้ปัญหาแบบทั่วไป (generic)

การออกแบบทางเลือกหนึ่งซึ่งใช้ประโยชน์จากเครื่องมือสำเร็จรูป (off-the-shelf tooling) คือการจัดเก็บข้อมูลการคลิกโฆษณาไว้ใน Hive พร้อมด้วยชั้น ElasticSearch ด้านบนที่สร้างขึ้นเพื่อ query ที่รวดเร็วขึ้น

การรวบรวมข้อมูลโดยทั่วไปมักทำในฐานข้อมูล OLAP เช่น ClickHouse หรือ Druid
