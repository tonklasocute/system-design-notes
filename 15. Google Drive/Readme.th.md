# บทที่ 15: ออกแบบ Google Drive (Design Google Drive)

## บทนำ
Google Drive คือบริการจัดเก็บและซิงค์ไฟล์บนคลาวด์ (cloud-based file storage and synchronization service) ที่ช่วยให้ผู้ใช้สามารถจัดเก็บ เข้าถึง และแชร์ไฟล์จากอุปกรณ์ต่าง ๆ ได้ บทนี้จะกล่าวถึงการออกแบบระบบที่สามารถขยายตัว (scalable) ได้ พร้อมด้วยฟีเจอร์ต่อไปนี้:
- **การอัปโหลดและดาวน์โหลดไฟล์ (File Upload and Download)**
- **การซิงค์ไฟล์ข้ามอุปกรณ์ (File Sync Across Devices)**
- **การแชร์ไฟล์ (File Sharing)**
- **ประวัติการแก้ไขไฟล์ (File Revision History)**
- **การแจ้งเตือนสำหรับการแก้ไข การลบ และการแชร์ (Notifications for Edits, Deletes, and Shares)**

---

## หัวข้อที่ 1: ทำความเข้าใจปัญหา (Understanding the Problem)

### ความต้องการหลัก (Key Requirements)
#### ความต้องการเชิงฟังก์ชัน (Functional Requirements):
- อัปโหลดและดาวน์โหลดไฟล์
- ซิงค์ไฟล์ข้ามอุปกรณ์หลายเครื่อง
- เก็บรักษาประวัติการแก้ไขไฟล์ (revisions)
- เปิดให้แชร์ไฟล์พร้อมกำหนดสิทธิ์ (permissions)
- ส่งการแจ้งเตือนเมื่อมีการแก้ไข ลบ หรือแชร์ไฟล์

#### ความต้องการเชิงไม่ใช่ฟังก์ชัน (Non-Functional Requirements):
- **ความน่าเชื่อถือ (Reliability):** ข้อมูลสูญหายเป็นสิ่งที่ยอมรับไม่ได้
- **ความเร็วในการซิงค์ (Fast Sync Speed):** หลีกเลี่ยงไม่ให้ผู้ใช้รู้สึกหงุดหงิดจากการซิงค์ที่ล่าช้า
- **ประสิทธิภาพการใช้แบนด์วิดท์ (Bandwidth Efficiency):** ลดการใช้ข้อมูลที่ไม่จำเป็นให้น้อยที่สุด
- **ความสามารถในการขยายระบบ (Scalability):** รองรับผู้ใช้งานที่ใช้งานจริงต่อวัน (DAU) 10 ล้านคน
- **ความพร้อมใช้งานสูง (High Availability):** ทำงานได้อย่างราบรื่นแม้เกิดความล้มเหลวของเซิร์ฟเวอร์หรือปัญหาเครือข่าย

### ข้อจำกัดและสมมติฐาน (Constraints and Assumptions)
- ผู้ใช้ได้รับพื้นที่ฟรี **10 GB**
- ขนาดไฟล์สูงสุด: **10 GB**
- ขนาดไฟล์อัปโหลดโดยเฉลี่ย: **500 KB**
- ความถี่ในการอัปโหลด: **2 ไฟล์ต่อวันต่อผู้ใช้**
- พื้นที่จัดเก็บข้อมูลรวมที่ต้องการ: **500 PB**

## หัวข้อที่ 2: การออกแบบระดับสูง (High-Level Design)
### การตั้งค่าเซิร์ฟเวอร์เดียว (Single-Server Setup)
การตั้งค่าพื้นฐานประกอบไปด้วย:
1. **เว็บเซิร์ฟเวอร์ (Web Server):** จัดการการอัปโหลดและดาวน์โหลด
2. **ฐานข้อมูลเมทาดาทา (Metadata Database):** ใช้ติดตามข้อมูลเมทาดาทา เช่น ข้อมูลผู้ใช้ ข้อมูลการล็อกอิน ข้อมูลไฟล์
3. **ไดเรกทอรีจัดเก็บ (Storage Directory):** เก็บไฟล์โดยจัดระเบียบตาม namespace


<div style="margin-left:3rem">
    <img src="./images/namespaces.png" alt="Namespaces" width="400" />
</div>

- เว็บเซิร์ฟเวอร์และไดเรกทอรีชื่อ drive/ ถูกตั้งค่าให้เป็น root directory สำหรับจัดเก็บไฟล์ที่อัปโหลด
- ภายใต้ไดเรกทอรี drive/ จะมีรายการไดเรกทอรีที่เรียกว่า namespace
- แต่ละ namespace เก็บไฟล์ที่ถูกอัปโหลดทั้งหมดของผู้ใช้คนนั้น
- แต่ละไฟล์หรือโฟลเดอร์สามารถระบุตัวตนได้อย่างไม่ซ้ำกันโดยการรวม namespace เข้ากับ relative path


การออกแบบนี้เป็นจุดเริ่มต้นที่ดี แต่ไม่เพียงพอต่อการขยายระบบ

#### APIs
1. **อัปโหลดไฟล์ไปยัง Google Drive:** รองรับการอัปโหลด 2 รูปแบบ
    - Simple upload: ใช้เมื่อไฟล์มีขนาดเล็ก
    - Resumable upload:
        - Endpoint: https://api.example.com/files/upload?uploadType=resumable
        - ส่ง request เริ่มต้นเพื่อขอรับ resumable URL
        - อัปโหลดข้อมูลและติดตามสถานะการอัปโหลด
        - หากการอัปโหลดถูกขัดจังหวะ ให้ทำการอัปโหลดต่อ (resume)
2. **ดาวน์โหลดไฟล์จาก Google Drive:** ในการดาวน์โหลดไฟล์
    -  Endpoint: https://api.example.com/files/download
3. **ดึงประวัติการแก้ไขไฟล์ (revisions):**
    - Endpoint: https://api.example.com/files/list_revisions

### ก้าวสู่ระบบแบบกระจาย (Moving to Distributed Systems)

#### การปรับปรุง (Improvements):
1. **Sharding:** แบ่งพื้นที่จัดเก็บออกไปหลายเซิร์ฟเวอร์ตาม `user_id`
2. **Amazon S3:** ใช้ S3 สำหรับจัดเก็บไฟล์ที่สามารถขยายตัวและมีความซ้ำซ้อน (redundant) พร้อมการทำสำเนาข้ามภูมิภาค (cross-region replication)

    <img src="./images/replication.png" alt="Replication" width="600" />

3. **Load Balancer:** กระจายทราฟฟิกไปยังเว็บเซิร์ฟเวอร์หลายตัว
4. **การทำสำเนาฐานข้อมูลเมทาดาทา (Metadata Database Replication):** รับประกันความพร้อมใช้งานผ่านการทำ sharding และ replication ของฐานข้อมูล


#### ความขัดแย้งในการซิงค์ (Sync Conflicts):
สำหรับระบบจัดเก็บขนาดใหญ่อย่าง Google Drive ความขัดแย้งในการซิงค์ (sync conflicts) เกิดขึ้นเป็นครั้งคราว
เมื่อผู้ใช้สองคนแก้ไขไฟล์หรือโฟลเดอร์เดียวกันในเวลาเดียวกัน จะเกิด conflict ขึ้น

<div style="margin-left:5rem">
<img src="./images/sync-conflicts.png" alt="Sync Conflicts" width="600" />
</div>

- ในตัวอย่างนี้ ผู้ใช้ 1 และผู้ใช้ 2 พยายามอัปเดตไฟล์เดียวกันในเวลาเดียวกัน แต่ระบบประมวลผลไฟล์ของผู้ใช้ 1 ก่อน
- การอัปเดตของผู้ใช้ 1 ผ่านไปได้ตามปกติ แต่ผู้ใช้ 2 จะพบกับ sync conflict
- ระบบจะแสดงไฟล์ทั้งสองเวอร์ชัน: สำเนาที่เก็บไว้ในเครื่องของผู้ใช้ 2 และเวอร์ชันล่าสุดจากเซิร์ฟเวอร์
- ผู้ใช้ 2 มีตัวเลือกที่จะรวม (merge) ไฟล์ทั้งสอง หรือเขียนทับเวอร์ชันหนึ่งด้วยอีกเวอร์ชันหนึ่ง

### การออกแบบที่ปรับปรุงแล้ว (Improved design)
<div style="margin-left:5rem">
<img src="./images/high-level-design.png" alt="High Level Design" width="500" />
</div>

1. **การปฏิสัมพันธ์ของผู้ใช้ (User Interaction):** ผู้ใช้เข้าถึงแอปพลิเคชันผ่านเบราว์เซอร์หรือแอปมือถือ

2. **Block Servers:**
   - ไฟล์จะถูกแบ่งเป็น **บล็อกขนาด 4 MB** (ขนาดสูงสุด) และกำหนดค่า hash ที่ไม่ซ้ำกันให้แต่ละบล็อก
   - บล็อกจะถูกจัดเก็บแยกจากกันในคลาวด์สตอเรจ (เช่น Amazon S3)
   - การประกอบไฟล์กลับคืน (file reconstruction) เกิดจากการนำบล็อกมาต่อกันตามลำดับที่กำหนด

3. **Cloud Storage:** บล็อกถูกจัดเก็บในคลาวด์สตอเรจเพื่อความสามารถในการขยายตัวและความซ้ำซ้อน

4. **Cold Storage:** ไฟล์ที่ไม่ได้ใช้งานจะถูกย้ายไปยัง cold storage เพื่อลดค่าใช้จ่าย

5. **Load Balancer:** กระจาย request อย่างเท่าเทียมไปยัง API server เพื่อให้การทำงานมีประสิทธิภาพ

6. **API Servers:**
   - จัดการเรื่องการยืนยันตัวตนผู้ใช้ (authentication) การจัดการโปรไฟล์ และการอัปเดตเมทาดาทาของไฟล์
   - จัดการ workflow ทั้งหมดที่ไม่ใช่การอัปโหลด

7. **Metadata Database และ Cache:**
   - จัดเก็บเมทาดาทาของผู้ใช้ ไฟล์ บล็อก และเวอร์ชัน
   - เมทาดาทาที่ถูกเข้าถึงบ่อยจะถูกแคชไว้เพื่อการดึงข้อมูลที่รวดเร็วขึ้น

8. **Notification Service:**
   - ระบบ **publisher/subscriber** ที่แจ้งเตือนไคลเอนต์เกี่ยวกับการเปลี่ยนแปลงไฟล์ (เพิ่ม แก้ไข ลบ)
   - รับประกันว่าไคลเอนต์สามารถดึง (pull) การอัปเดตล่าสุดได้

9. **Offline Backup Queue:** จัดเก็บข้อมูลการเปลี่ยนแปลงไฟล์ไว้ชั่วคราวสำหรับไคลเอนต์ที่ออฟไลน์ เพื่อให้ซิงค์ได้เมื่อกลับมาออนไลน์

## หัวข้อที่ 3: เจาะลึกการออกแบบ (Design Deep Dive)

### ฐานข้อมูลเมทาดาทา (Metadata Database)
ด้านล่างแสดงเวอร์ชันที่ถูกทำให้ง่ายขึ้นมาก โดยมีเพียงตารางและฟิลด์ที่สำคัญที่สุด
#### การออกแบบ Schema (Schema Design):
- **User Table:** จัดเก็บโปรไฟล์และการตั้งค่าของผู้ใช้
- **File Table:** เก็บรักษาเมทาดาทาของไฟล์ (เช่น ขนาด ชื่อ พาธ)
- **Block Table:** ติดตามบล็อกไฟล์เพื่อใช้ในการประกอบไฟล์กลับคืน
- **File Version Table:** จัดเก็บประวัติการแก้ไขไฟล์ (revision history)

### ลำดับการอัปโหลดไฟล์ (File Upload Flow)

1. **การอัปโหลดไฟล์ (File Upload):**
   - ไฟล์จะถูกแบ่งเป็นบล็อก บีบอัด (compressed) และเข้ารหัส (encrypted) โดย block server
   - บล็อกจะถูกอัปโหลดไปยัง block server และจัดเก็บไว้ใน S3
2. **การอัปโหลดเมทาดาทา (Metadata Upload):**
   - ไคลเอนต์ส่งเมทาดาทาไปยัง API server
   - เมทาดาทาถูกจัดเก็บในฐานข้อมูลด้วยสถานะ `pending`
3. **การเสร็จสิ้น (Completion):**
   - S3 จะทริกเกอร์ callback เพื่ออัปเดตสถานะไฟล์เป็น `uploaded`
   - Notification service แจ้งเตือนผู้ใช้ที่เกี่ยวข้อง

### การซิงค์ไฟล์ (File Sync)
1. **Delta Sync:** ส่งเฉพาะบล็อกที่มีการแก้ไข แทนที่จะส่งไฟล์ทั้งหมด

    <div style="margin-left:2rem">

2. **การบีบอัด (Compression):** บล็อกจะถูกบีบอัดด้วยอัลกอริทึมการบีบอัด (compression algorithms) ที่แตกต่างกันไปตามประเภทไฟล์
3. **การแก้ไขความขัดแย้ง (Conflict Resolution):**
   - เวอร์ชันที่ถูกประมวลผลก่อนจะเป็นฝ่ายชนะ
   - เวอร์ชันที่ขัดแย้งกันจะถูกบันทึกแยกไว้ต่างหากเพื่อให้ผู้ใช้แก้ไขเอง

### ลำดับการดาวน์โหลดไฟล์ (File Download Flow)
ลำดับการดาวน์โหลดจะถูกทริกเกอร์เมื่อมีการเพิ่มหรือแก้ไขไฟล์จากที่อื่น มีสองวิธีที่ไคลเอนต์จะทราบได้:
- หากไคลเอนต์ A ออนไลน์อยู่ในขณะที่ไฟล์ถูกเปลี่ยนแปลงโดยไคลเอนต์อื่น notification service จะแจ้งเตือนไคลเอนต์ A
- หากไคลเอนต์ A ออฟไลน์อยู่ในขณะที่ไฟล์ถูกเปลี่ยนแปลงโดยไคลเอนต์อื่น ข้อมูลจะถูกบันทึกไว้ในแคช เมื่อไคลเอนต์ที่ออฟไลน์กลับมาออนไลน์อีกครั้ง มันจะดึง (pull) การเปลี่ยนแปลงล่าสุด

เมื่อไคลเอนต์ทราบว่าไฟล์มีการเปลี่ยนแปลง มันจะร้องขอเมทาดาทาผ่าน API server ก่อน จากนั้นจึง
ดาวน์โหลดบล็อกเพื่อประกอบไฟล์ขึ้นมาใหม่

1. **การทริกเกอร์ (Trigger):** Notification service แจ้งไคลเอนต์ถึงการอัปเดตไฟล์
2. **การดึงเมทาดาทา (Metadata Fetch):** ไคลเอนต์ดึงเมทาดาทาที่อัปเดตแล้วผ่าน API
3. **การดาวน์โหลดบล็อก (Block Download):** ไคลเอนต์ดาวน์โหลดบล็อกที่อัปเดตจาก block server และประกอบไฟล์กลับคืน

### Notification Service
1. **จุดประสงค์ (Purpose):** ทำให้ไคลเอนต์รับทราบการเปลี่ยนแปลงไฟล์อยู่เสมอ
2. **กลไก (Mechanism):** ใช้ **long polling** สำหรับการแจ้งเตือนแบบอะซิงโครนัส (asynchronous)
3. **ตัวอย่าง (Example):** เมื่อไฟล์ถูกเพิ่ม แก้ไข หรือลบ การแจ้งเตือนจะถูก push ไปยังไคลเอนต์ที่เกี่ยวข้องทั้งหมด


---

### การเพิ่มประสิทธิภาพการจัดเก็บ (Storage Optimization)
1. **การกำจัดข้อมูลซ้ำ (De-duplication):** ลบบล็อกที่ซ้ำกันในระดับบัญชี (account level) โดยใช้การเปรียบเทียบด้วย hash
2. **กลยุทธ์การเก็บเวอร์ชัน (Versioning Strategy):**
   - จำกัดจำนวนการเก็บ revision
   - ให้ความสำคัญกับเวอร์ชันล่าสุดสำหรับไฟล์ที่ถูกแก้ไขบ่อย
3. **Cold Storage:** ย้ายไฟล์ที่ไม่ค่อยถูกเข้าถึงไปยังโซลูชันการจัดเก็บที่มีราคาถูกกว่า (เช่น Amazon S3 Glacier)

---

### การจัดการความล้มเหลว (Failure Handling)
1. **ความล้มเหลวของ Load Balancer:** Load balancer สำรอง (secondary) จะเข้ามาทำงานแทน
2. **ความล้มเหลวของ Block Server:** งานที่ค้างอยู่ (pending tasks) จะถูกมอบหมายใหม่ไปยังเซิร์ฟเวอร์ตัวอื่น
3. **ความล้มเหลวของ Metadata Database:**
   - Promote slave node ตัวหนึ่งขึ้นเป็น master
   - เปลี่ยนเส้นทางทราฟฟิกไปยัง replica ที่เหลืออยู่
4. **ความล้มเหลวของ Cloud Storage:** ใช้การทำสำเนาข้ามภูมิภาค (cross-region replication) เพื่อดึงไฟล์ที่ไม่พร้อมใช้งาน
5. **ความล้มเหลวของ Notification Service:** ไคลเอนต์จะเชื่อมต่อใหม่ไปยังเซิร์ฟเวอร์สำรองอื่น
