# บทที่ 23: บริการอีเมลแบบกระจาย (Distributed Email Service)

## บทนำ

ในบทนี้เราจะออกแบบ **บริการอีเมลแบบกระจาย (Distributed Email Service)** ที่คล้ายกับ **Gmail**

ในปี 2020 **Gmail** มีผู้ใช้งานที่ยังทำงานอยู่ (active users) 1.8 พันล้านคน ในขณะที่ **Outlook** มีผู้ใช้งาน 400 ล้านคนทั่วโลก

---

## ขั้นตอนที่ 1: ทำความเข้าใจปัญหาและกำหนดขอบเขตการออกแบบ (Understand the Problem and Establish Design Scope)

- C: ระบบมีผู้ใช้งานกี่คน
- I: 1 พันล้านคน
- C: ผมคิดว่าฟีเจอร์ต่อไปนี้มีความสำคัญ - การยืนยันตัวตน (auth), การส่ง/รับอีเมล, การดึงอีเมล (fetch email), การกรองอีเมล (filter emails), การค้นหาอีเมล (search email), การป้องกันสแปม (anti-spam protection)
- I: รายการดี ไม่ต้องกังวลเรื่อง auth ตอนนี้
- C: ผู้ใช้เชื่อมต่อกับเซิร์ฟเวอร์อีเมลอย่างไร
- I: โดยทั่วไป email client จะเชื่อมต่อผ่าน SMTP, POP, IMAP แต่สำหรับโจทย์นี้เราจะใช้ HTTP
- C: อีเมลสามารถมีไฟล์แนบ (attachments) ได้หรือไม่
- I: ได้

### **ความต้องการที่ไม่ใช่เชิงฟังก์ชัน (Non-functional requirements)**

- **ความน่าเชื่อถือ (Reliability)** - เราไม่ควรทำข้อมูลสูญหาย
- **ความพร้อมใช้งาน (Availability)** - เราควรใช้การทำสำเนาข้อมูล (replication) เพื่อป้องกันจุดที่ทำให้ระบบล้มเหลวทั้งหมด (single point of failure) เราควรทนทานต่อความล้มเหลวบางส่วนของระบบด้วย
- **ความสามารถในการขยาย (Scalability)** - เมื่อฐานผู้ใช้เติบโตขึ้น ระบบของเราควรสามารถรองรับได้
- **ความยืดหยุ่นและความสามารถในการต่อขยาย (Flexibility and extensibility)** - ระบบควรมีความยืดหยุ่นและง่ายต่อการต่อขยายด้วยฟีเจอร์ใหม่ ๆ นี่เป็นหนึ่งในเหตุผลที่เราเลือกใช้ HTTP แทนที่จะเป็น SMTP หรือโปรโตคอลเมลอื่น ๆ

### **การประมาณการคร่าว ๆ (Back-of-the-envelope estimation)**

- **ผู้ใช้ 1 พันล้านคน**
- สมมติว่าหนึ่งคนส่งอีเมล 10 ฉบับต่อวัน -> **100,000 อีเมลต่อวินาที**
- สมมติว่าหนึ่งคนรับอีเมล 40 ฉบับต่อวัน และแต่ละอีเมลมีข้อมูล metadata เฉลี่ย 50kb -> **730pb ของพื้นที่จัดเก็บต่อปี**
- สมมติว่า 20% ของอีเมลมีไฟล์แนบที่ต้องจัดเก็บ และขนาดเฉลี่ยอยู่ที่ 500kb -> **1,460pb ต่อปี**

## ขั้นตอนที่ 2: นำเสนอการออกแบบระดับสูงและขอความเห็นชอบ (Propose High-Level Design and Get Buy-In)

### **ความรู้พื้นฐานเกี่ยวกับอีเมล (Email knowledge 101)**

มีโปรโตคอลหลายแบบที่ใช้สำหรับการส่งและรับอีเมล:
- **SMTP** - โปรโตคอลมาตรฐานสำหรับส่งอีเมลจากเซิร์ฟเวอร์หนึ่งไปยังอีกเซิร์ฟเวอร์หนึ่ง
- **POP** - โปรโตคอลมาตรฐานสำหรับรับและดาวน์โหลดอีเมลจากเมลเซิร์ฟเวอร์ระยะไกลมายัง client ที่เครื่อง เมื่อดึงข้อมูลมาแล้ว อีเมลจะถูกลบออกจากเซิร์ฟเวอร์ระยะไกล
- **IMAP** - คล้ายกับ POP ใช้สำหรับรับและดาวน์โหลดอีเมลจากเซิร์ฟเวอร์ระยะไกล แต่จะเก็บอีเมลไว้ที่ฝั่งเซิร์ฟเวอร์
- **HTTPS** - ไม่ใช่โปรโตคอลอีเมลโดยแท้จริง แต่สามารถใช้กับ email client แบบเว็บได้

นอกเหนือจากโปรโตคอลการรับส่งเมลแล้ว ยังมี DNS record บางส่วนที่เราต้องกำหนดค่าให้กับเมลเซิร์ฟเวอร์ของเรา นั่นคือ MX record:

<div style="margin-left:3rem">
    <img src="./images/dns-lookup.png" alt="dns-lookup" width="500" />
</div>

ไฟล์แนบในอีเมลจะถูกส่งในรูปแบบ base64-encoded และโดยทั่วไปจะมีขีดจำกัดขนาดอยู่ที่ 25mb บนบริการเมลส่วนใหญ่
ซึ่งสามารถปรับตั้งค่าได้และแตกต่างกันไปตามบัญชีส่วนบุคคลและบัญชีองค์กร

### **เมลเซิร์ฟเวอร์แบบดั้งเดิม (Traditional mail servers)**

เมลเซิร์ฟเวอร์แบบดั้งเดิมทำงานได้ดีเมื่อมีจำนวนผู้ใช้จำกัด และเชื่อมต่อกับเซิร์ฟเวอร์เดียว

<div style="margin-left:3rem">
    <img src="./images/traditional-mail-server.png" alt="traditional-mail-server" width="500" />
</div>

- Alice ล็อกอินเข้าอีเมล Outlook ของเธอและกดปุ่ม "ส่ง" อีเมลจะถูกส่งไปยังเมลเซิร์ฟเวอร์ของ Outlook การสื่อสารเป็นผ่าน SMTP
- เซิร์ฟเวอร์ Outlook จะค้นหา DNS เพื่อหา MX record ของ gmail.com และส่งต่ออีเมลไปยังเซิร์ฟเวอร์ของ Gmail การสื่อสารเป็นผ่าน SMTP
- Bob ดึงอีเมลจากเซิร์ฟเวอร์ Gmail ของเขาผ่าน IMAP/POP

ในเมลเซิร์ฟเวอร์แบบดั้งเดิม อีเมลถูกจัดเก็บไว้บนระบบไฟล์ในเครื่อง (local file system) โดยแต่ละอีเมลเป็นไฟล์แยกกัน

<div style="margin-left:3rem">
    <img src="./images/local-dir-storage.png" alt="local-dir-storage" width="500" />
</div>

เมื่อขนาดของระบบเติบโตขึ้น disk I/O กลายเป็นคอขวด (bottleneck) นอกจากนี้ยังไม่ตอบสนองความต้องการด้านความพร้อมใช้งานสูง (high availability) และความน่าเชื่อถือ (reliability) ของเรา
ดิสก์สามารถเสียหายได้และเซิร์ฟเวอร์สามารถล่มได้

### **เมลเซิร์ฟเวอร์แบบกระจาย (Distributed mail servers)**

เมลเซิร์ฟเวอร์แบบกระจายถูกออกแบบมาเพื่อรองรับกรณีการใช้งานสมัยใหม่และแก้ปัญหาด้านความสามารถในการขยายในยุคปัจจุบัน

เซิร์ฟเวอร์เหล่านี้ยังคงรองรับ IMAP/POP สำหรับ email client ดั้งเดิม (native) และ SMTP สำหรับการแลกเปลี่ยนเมลระหว่างเซิร์ฟเวอร์

แต่สำหรับ web-based mail client ที่มีความสามารถหลากหลาย มักจะใช้ RESTful API ผ่าน HTTP

ตัวอย่าง API:
- `POST /v1/messages` - ส่งข้อความไปยังผู้รับใน header To, Cc, Bcc
- `GET /v1/folders` - คืนค่าโฟลเดอร์ทั้งหมดของบัญชีอีเมล

ตัวอย่างการตอบกลับ:

```
[{id: string        Unique folder identifier.
  name: string      Name of the folder.
                    According to RFC6154 [9], the default folders can be one of
                    the following: All, Archive, Drafts, Flagged, Junk, Sent,
                    and Trash.
  user_id: string   Reference to the account owner
}]
```

- `GET /v1/folders/{:folder_id}/messages` - คืนค่าข้อความทั้งหมดภายใต้โฟลเดอร์หนึ่ง พร้อม pagination
- `GET /v1/messages/{:message_id}` - รับข้อมูลทั้งหมดของข้อความหนึ่ง ๆ

ตัวอย่างการตอบกลับ:

```
{
  user_id: string                      // Reference to the account owner.
  from: {name: string, email: string}  // <name, email> pair of the sender.
  to: [{name: string, email: string}]  // A list of <name, email> paris
  subject: string                      // Subject of an email
  body: string                         //  Message body
  is_read: boolean                     //  Indicate if a message is read or not.
}
```

ต่อไปนี้คือการออกแบบระดับสูงของเมลเซิร์ฟเวอร์แบบกระจาย:

<div style="margin-left:3rem">
    <img src="./images/high-level-architecture.png" alt="high-level-architecture" width="500" />
</div>

- **Webmail** - ผู้ใช้ใช้เว็บเบราว์เซอร์ในการส่ง/รับอีเมล
- **Web servers** - บริการ request/response ที่เปิดให้สาธารณะเข้าถึง ใช้จัดการการล็อกอิน, การสมัครสมาชิก, โปรไฟล์ผู้ใช้ ฯลฯ
- **Real-time servers** - ใช้สำหรับ push ข้อมูลอัปเดตอีเมลใหม่ไปยัง client แบบเรียลไทม์ เราใช้ websocket สำหรับการสื่อสารแบบเรียลไทม์ แต่จะ fallback ไปใช้ long-polling สำหรับเบราว์เซอร์รุ่นเก่าที่ไม่รองรับ
- **Metadata db** - จัดเก็บ metadata ของอีเมล เช่น subject, body, from, to ฯลฯ
- **Attachment store** - Object store (เช่น Amazon S3) เหมาะสำหรับจัดเก็บไฟล์ขนาดใหญ่
- **Distributed cache** - เราสามารถแคชอีเมลล่าสุดไว้ใน Redis เพื่อปรับปรุงประสบการณ์ผู้ใช้ (UX)
- **Search store** - document store แบบกระจาย ใช้รองรับการค้นหาแบบ full-text

นี่คือลักษณะการทำงานของ flow การส่งอีเมล:

</div>

- ผู้ใช้เขียนอีเมลและกดปุ่ม "ส่ง" อีเมลจะถูกส่งไปยัง load balancer
- Load balancer จะจำกัดอัตราการส่งเมลที่มากเกินไป (rate limit) และ route ไปยังหนึ่งใน web server
- Web server จะทำการตรวจสอบความถูกต้องพื้นฐานของอีเมล (เช่น ขนาดอีเมล) และตัด flow ขาออกทันทีหากโดเมนเดียวกันกับผู้ส่ง แต่จะทำการตรวจสอบสแปมก่อนเสมอ
- หากผ่านการตรวจสอบพื้นฐาน อีเมลจะถูกส่งไปยัง message queue (ไฟล์แนบจะถูกอ้างอิงจาก object store)
- หากไม่ผ่านการตรวจสอบพื้นฐาน อีเมลจะถูกส่งไปยัง error queue
- SMTP outgoing worker จะดึงข้อความจาก outgoing queue ทำการตรวจสอบสแปม/ไวรัส และ route ไปยังเมลเซิร์ฟเวอร์ปลายทาง
- อีเมลจะถูกจัดเก็บในโฟลเดอร์ "Sent Emails"

เรายังต้องมอนิเตอร์ขนาดของ outgoing message queue ด้วย เพราะการเติบโตขนาดใหญ่เกินไปอาจบ่งชี้ถึงปัญหา:
- เมลเซิร์ฟเวอร์ของผู้รับไม่พร้อมใช้งาน เราสามารถลองส่งอีเมลใหม่ในภายหลังโดยใช้ exponential backoff
- consumer ไม่เพียงพอต่อการรองรับภาระงาน อาจจำเป็นต้อง scale consumer

- อีเมลขาเข้าจะมาถึง SMTP load balancer เมลจะถูกกระจายไปยัง SMTP server ซึ่งจะทำการตรวจสอบนโยบายการยอมรับเมล (mail acceptance policy) ที่นี่ (เช่น อีเมลที่ไม่ถูกต้องจะถูกทิ้งทันที)
- หากไฟล์แนบของอีเมลมีขนาดใหญ่เกินไป เราสามารถเก็บไว้ใน object store (s3) ได้
- Mail processing worker จะทำการตรวจสอบเบื้องต้น หลังจากนั้นเมลจะถูกส่งต่อไปยัง storage, cache, object store และ real-time server
- ผู้ใช้ที่ออฟไลน์อยู่จะได้รับอีเมลใหม่เมื่อกลับมาออนไลน์ ผ่านทาง HTTP API

## ขั้นตอนที่ 3: เจาะลึกการออกแบบ (Design Deep Dive)

มาเจาะลึกลงในบางคอมโพเนนต์กันต่อ

### **ฐานข้อมูล Metadata (Metadata database)**

นี่คือคุณลักษณะบางประการของ metadata อีเมล:
- header มักจะมีขนาดเล็กและถูกเข้าถึงบ่อย
- ขนาดของ body มีตั้งแต่เล็กไปจนถึงใหญ่ แต่โดยทั่วไปจะถูกอ่านเพียงครั้งเดียว
- การดำเนินการส่วนใหญ่ของเมลถูกจำกัดอยู่ภายในผู้ใช้คนเดียว เช่น การดึงอีเมล, การทำเครื่องหมายว่าอ่านแล้ว, การค้นหา
- ความสดใหม่ของข้อมูล (data recency) ส่งผลต่อการใช้งานข้อมูล โดยทั่วไปผู้ใช้จะอ่านเฉพาะอีเมลล่าสุดเท่านั้น
- ข้อมูลมีความต้องการด้านความน่าเชื่อถือสูง การสูญหายของข้อมูลเป็นสิ่งที่ยอมรับไม่ได้

ในระดับขนาดของ Gmail/Outlook ฐานข้อมูลมักถูกสร้างขึ้นมาเอง (custom made) เพื่อลดจำนวนการดำเนินการอ่าน/เขียนต่อวินาที (input/output operations per second หรือ IOPS)

มาพิจารณาตัวเลือกฐานข้อมูลที่เรามีกัน:
- **ฐานข้อมูลเชิงสัมพันธ์ (Relational database)** - เราสามารถสร้าง index สำหรับ header และ body ได้ แต่ฐานข้อมูลประเภทนี้มักถูกปรับให้เหมาะสมสำหรับข้อมูลชิ้นเล็ก ๆ
- **Distributed object store** - เป็นตัวเลือกที่ดีสำหรับการเก็บสำรอง (backup storage) แต่ไม่สามารถรองรับการค้นหา/การทำเครื่องหมายว่าอ่านแล้ว ฯลฯ ได้อย่างมีประสิทธิภาพ
- **NoSQL** - Google BigTable ถูกใช้โดย Gmail แต่ไม่ใช่ open-source

จากการวิเคราะห์ข้างต้น มีโซลูชันที่มีอยู่แล้วเพียงไม่กี่ตัวที่เหมาะกับความต้องการของเราอย่างสมบูรณ์
ในบริบทของการสัมภาษณ์ การออกแบบฐานข้อมูลแบบกระจายขึ้นมาใหม่ทั้งหมดนั้นไม่สามารถทำได้จริง แต่สิ่งสำคัญคือต้องกล่าวถึงคุณลักษณะต่อไปนี้:
- คอลัมน์เดียวสามารถมีขนาดได้ถึงหลัก MB หลักเดียว
- ความสอดคล้องของข้อมูลที่เข้มงวด (strong data consistency)
- ถูกออกแบบมาเพื่อลด disk I/O
- มีความพร้อมใช้งานสูงและทนทานต่อความผิดพลาด (fault tolerant)
- ควรสร้าง incremental backup ได้ง่าย

เพื่อแบ่งพาร์ทิชันข้อมูล เราสามารถใช้ `user_id` เป็น partition key เพื่อให้ข้อมูลของผู้ใช้คนหนึ่งถูกจัดเก็บอยู่บน shard เดียว
วิธีนี้ทำให้เราไม่สามารถแชร์อีเมลระหว่างผู้ใช้หลายคนได้ แต่นี่ไม่ใช่ข้อกำหนดสำหรับการสัมภาษณ์นี้

มาลองกำหนดตารางกัน:
- Primary key ประกอบด้วย partition key (ใช้กระจายข้อมูล) และ clustering key (ใช้จัดเรียงข้อมูล)
- คิวรีที่เราต้องรองรับ - รับโฟลเดอร์ทั้งหมดของผู้ใช้, แสดงอีเมลทั้งหมดในโฟลเดอร์, สร้าง/รับ/ลบอีเมล, ดึงอีเมลที่อ่านแล้ว/ยังไม่ได้อ่าน, รับ conversation thread (โบนัส)

### **ความสามารถในการส่งอีเมลถึงปลายทาง (Email deliverability)**

การตั้งค่าเซิร์ฟเวอร์เพื่อส่งอีเมลนั้นทำได้ง่าย แต่การทำให้อีเมลไปถึงกล่องขาเข้าของผู้รับนั้นยาก เนื่องจากอัลกอริทึมป้องกันสแปม

หากเราเพียงแค่ตั้งค่าเมลเซิร์ฟเวอร์ใหม่ขึ้นมาแล้วเริ่มส่งเมลผ่านมัน อีเมลของเราน่าจะไปจบลงที่โฟลเดอร์สแปม

นี่คือสิ่งที่เราสามารถทำได้เพื่อป้องกันปัญหานี้:
- **IP เฉพาะ (Dedicated IPs)** - ใช้ IP เฉพาะสำหรับการส่งอีเมล มิฉะนั้นเซิร์ฟเวอร์ของผู้รับจะไม่ไว้วางใจคุณ
- **จัดหมวดหมู่อีเมล (Classify emails)** - หลีกเลี่ยงการส่งอีเมลการตลาดจากเซิร์ฟเวอร์เดียวกัน เพื่อป้องกันไม่ให้อีเมลที่สำคัญกว่าถูกจัดเป็นสแปม
- **อุ่นเครื่อง (Warm up) IP address** อย่างช้า ๆ เพื่อสร้างชื่อเสียงที่ดีกับผู้ให้บริการอีเมลรายใหญ่ ใช้เวลา 2 ถึง 6 สัปดาห์ในการอุ่นเครื่อง IP ใหม่
- **แบน (Ban) สแปมเมอร์** อย่างรวดเร็วเพื่อไม่ให้ชื่อเสียงของเราเสื่อมลง
- **การประมวลผล feedback (Feedback processing)** - ตั้งค่า feedback loop กับ ISP เพื่อติดตามอัตราการร้องเรียนและแบนบัญชีสแปมอย่างรวดเร็ว
- **การยืนยันตัวตนอีเมล (Email authentication)** - ใช้เทคนิคทั่วไปในการต่อต้านฟิชชิ่ง เช่น Sender Policy Framework, DomainKeys Identified Mail ฯลฯ

คุณไม่จำเป็นต้องจำทั้งหมดนี้ เพียงแค่รู้ว่าการสร้างเมลเซิร์ฟเวอร์ที่ดีต้องอาศัยความรู้เฉพาะทางจำนวนมาก

### **การค้นหา (Search)**

การค้นหารวมถึงการทำ full-text search จากเนื้อหาอีเมล หรือคิวรีขั้นสูงกว่านั้นตามฟิลเตอร์ from, to, subject, unread ฯลฯ

คุณลักษณะหนึ่งของการค้นหาอีเมลคือมันเป็นข้อมูลเฉพาะของผู้ใช้แต่ละคน (local to the user) และมีการเขียนมากกว่าการอ่าน เนื่องจากเราจำเป็นต้อง re-index ในทุกการดำเนินการ แต่ผู้ใช้แทบจะไม่ค่อยใช้แท็บค้นหา

มาเปรียบเทียบการค้นหาของ Google กับการค้นหาอีเมลกัน:

|               | ขอบเขต (Scope)                | การจัดเรียง (Sorting)                               | ความแม่นยำ (Accuracy)                                          |
|---------------|----------------------|---------------------------------------|---------------------------------------------------|
| Google search | อินเทอร์เน็ตทั้งหมด   | จัดเรียงตามความเกี่ยวข้อง (relevance)                     | การทำ index ใช้เวลาสักครู่ ผลลัพธ์จึงไม่ทันที |
| Email search  | กล่องอีเมลของผู้ใช้เอง | จัดเรียงตามคุณสมบัติ (attributes) เช่น เวลา, วันที่ ฯลฯ | การทำ index ควรรวดเร็วและผลลัพธ์ต้องแม่นยำ    |

เพื่อให้บรรลุความสามารถในการค้นหานี้ ทางเลือกหนึ่งคือใช้ Elasticsearch cluster เราสามารถใช้ `user_id` เป็น partition key เพื่อจัดกลุ่มข้อมูลไว้บน node เดียวกัน:

<div style="margin-left:3rem">
    <img src="./images/elasticsearch.png" alt="elasticsearch" width="500" />
</div>

การดำเนินการที่เปลี่ยนแปลงข้อมูล (mutating operations) จะทำงานแบบ async ผ่าน Kafka เพื่อแยก (decouple) บริการออกจาก flow การ reindex
ส่วนการค้นหาข้อมูลจริง ๆ จะเกิดขึ้นแบบ synchronous

Elasticsearch เป็นหนึ่งในฐานข้อมูลเครื่องมือค้นหาที่ได้รับความนิยมมากที่สุด และรองรับการทำ full-text search สำหรับอีเมลได้เป็นอย่างดี

อีกทางเลือกหนึ่ง เราสามารถพยายามพัฒนาโซลูชันการค้นหาที่กำหนดเองขึ้นมาเพื่อตอบสนองความต้องการเฉพาะของเรา

การออกแบบระบบเช่นนี้อยู่นอกขอบเขตของบทนี้ หนึ่งในความท้าทายหลักของการสร้างระบบนี้คือการปรับให้เหมาะสมกับภาระงานที่มีการเขียนหนัก (write-heavy workload)

เพื่อให้บรรลุสิ่งนี้ เราสามารถใช้ Log-Structured Merge-Trees (LSM) เพื่อจัดโครงสร้างข้อมูล index บนดิสก์ได้ เส้นทางการเขียน (write path) จะถูกปรับให้เหมาะสมสำหรับการเขียนแบบต่อเนื่อง (sequential) เท่านั้น
เทคนิคนี้ถูกใช้ใน Cassandra, BigTable และ RocksDB

แนวคิดหลักของมันคือการจัดเก็บข้อมูลไว้ในหน่วยความจำ (in-memory) จนกว่าจะถึงเกณฑ์ที่กำหนดไว้ล่วงหน้า จากนั้นจึงจะถูก merge เข้าไปในเลเยอร์ถัดไป (ดิสก์):

<div style="margin-left:3rem">
    <img src="./images/lsm-tree.png" alt="lsm-tree" width="500" />
</div>

ข้อแลกเปลี่ยน (trade-offs) หลักระหว่างสองแนวทาง:
- Elasticsearch สามารถขยาย (scale) ได้ในระดับหนึ่ง ในขณะที่ search engine แบบกำหนดเองสามารถปรับจูนอย่างละเอียด (fine-tuned) สำหรับกรณีใช้งานอีเมลได้ ทำให้ขยายต่อไปได้มากกว่า
- Elasticsearch เป็นบริการแยกต่างหากที่เราต้องดูแล นอกเหนือจาก metadata store ในขณะที่โซลูชันแบบกำหนดเองสามารถเป็น datastore เดียวกันได้เลย
- Elasticsearch เป็นโซลูชันสำเร็จรูป (off-the-shelf) ในขณะที่ search engine แบบกำหนดเองต้องใช้ความพยายามด้านวิศวกรรมอย่างมากในการสร้าง

### **ความสามารถในการขยายและความพร้อมใช้งาน (Scalability and availability)**

เนื่องจากการดำเนินการของผู้ใช้แต่ละคนไม่ชนกับผู้ใช้คนอื่น คอมโพเนนต์ส่วนใหญ่จึงสามารถขยาย (scale) ได้อย่างอิสระต่อกัน

เพื่อให้มั่นใจถึงความพร้อมใช้งานสูง เรายังสามารถใช้การตั้งค่าแบบ multi-DC พร้อมกับ leader-follower failover ในกรณีที่เกิดความล้มเหลวได้:

## ขั้นตอนที่ 4: สรุป (Wrap Up)

ประเด็นเพิ่มเติมที่ควรพูดถึง:
- **ความทนทานต่อความผิดพลาด (Fault tolerance)** - หลายส่วนของระบบอาจเกิดความล้มเหลวได้ จึงควรพิจารณาว่าเราจะจัดการกับความล้มเหลวของ node อย่างไร
- **การปฏิบัติตามข้อกำหนด (Compliance)** - ข้อมูลที่สามารถระบุตัวตนได้ (PII) จำเป็นต้องถูกจัดเก็บอย่างเหมาะสม ตามกฎหมาย GDPR ของยุโรป
- **ความปลอดภัย (Security)** - การเข้ารหัสอีเมล, การป้องกันฟิชชิ่ง, การท่องเว็บอย่างปลอดภัย ฯลฯ
- **การปรับให้เหมาะสม (Optimizations)** - เช่น การป้องกันการซ้ำซ้อนของไฟล์แนบเดียวกันที่ถูกส่งหลายครั้งโดยผู้ใช้ต่างคนกัน
