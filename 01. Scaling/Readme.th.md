# บทที่ 1: การขยายระบบจากศูนย์สู่ผู้ใช้งานหลักล้านคน (Scale from Zero to Millions of Users)

## บทนำ
การขยายระบบ (Scaling) เพื่อรองรับผู้ใช้งานหลักล้านคนเป็นกระบวนการที่ซับซ้อนและต้องทำแบบวนซ้ำ (iterative) โดยต้องมีการปรับปรุงและ optimize อยู่เสมอ บทนี้จะอธิบายวิธีการเริ่มต้นจากเซิร์ฟเวอร์เดียว แล้วค่อย ๆ ขยายสถาปัตยกรรมทีละขั้นตอนจนสามารถรองรับผู้ใช้งานหลักล้านคนได้

---

## หัวข้อที่ 1: การตั้งค่าเซิร์ฟเวอร์เดียว (Single Server Setup)
ในช่วงแรก คอมโพเนนต์ทั้งหมด (เว็บแอป, ฐานข้อมูล, แคช) จะรันอยู่บนเซิร์ฟเวอร์เดียวกัน

<div style="margin-left:3rem">
   <img src="./images/single-server.png" width="400" />
</div>

### ลำดับการทำงานของ Request (Request Flow)
1. ผู้ใช้เข้าถึงแอปพลิเคชันผ่านชื่อโดเมน (เช่น `api.mysite.com`) ซึ่งจะถูกแปลงเป็น IP address ผ่านระบบ DNS
2. IP address ของเว็บเซิร์ฟเวอร์จะถูกส่งกลับไปยังเบราว์เซอร์หรือแอปมือถือ
3. HTTP request จะถูกส่งไปยังเว็บเซิร์ฟเวอร์ ซึ่งจะตอบกลับมาเป็น HTML หรือ JSON

### แหล่งที่มาของทราฟฟิก (Traffic Sources)
1. **เว็บแอปพลิเคชัน:** ใช้ภาษาฝั่งเซิร์ฟเวอร์ (server-side language เช่น Python, Java) สำหรับ business logic และภาษาฝั่งไคลเอนต์ (client-side language เช่น JavaScript, HTML) สำหรับการแสดงผล (presentation)
2. **แอปพลิเคชันมือถือ:** สื่อสารกับเว็บเซิร์ฟเวอร์โดยใช้ HTTP และ JSON เพื่อแลกเปลี่ยนข้อมูลแบบน้ำหนักเบา (lightweight)

---

## หัวข้อที่ 2: การแยกฐานข้อมูลออกจากเว็บเซิร์ฟเวอร์ (Database Separation)
เมื่อจำนวนผู้ใช้เพิ่มขึ้น ฐานข้อมูลจะถูกย้ายไปอยู่บนเซิร์ฟเวอร์แยกต่างหาก เพื่อให้สามารถขยาย (scale) ชั้นเว็บ (web tier) และชั้นฐานข้อมูล (database tier) ได้อย่างอิสระจากกัน

<div style="margin-left:3rem">
   <img src="./images/database.png" width="400" />
</div>

### ทางเลือกของฐานข้อมูล (Database Choices)

1. **ฐานข้อมูลเชิงสัมพันธ์ (Relational Databases / SQL):** จัดเก็บข้อมูลแบบมีโครงสร้างในรูปแบบตาราง ตัวอย่างเช่น MySQL, PostgreSQL
2. **ฐานข้อมูลแบบไม่ใช่เชิงสัมพันธ์ (Non-Relational Databases / NoSQL):** เหมาะสำหรับข้อมูลที่ไม่มีโครงสร้างชัดเจน หรือมีความต้องการ latency ต่ำมาก แบ่งออกเป็นหมวดหมู่ต่าง ๆ ได้แก่
   - Key-Value Stores
   - Graph Databases
   - Column Stores
   - Document Stores

- ฐานข้อมูลแบบไม่ใช่เชิงสัมพันธ์อาจเป็นตัวเลือกที่เหมาะสมกว่า หากเข้าเงื่อนไขต่อไปนี้:
   - แอปพลิเคชันต้องการ latency ที่ต่ำมาก ๆ
   - ข้อมูลไม่มีโครงสร้าง (unstructured) หรือไม่มีความสัมพันธ์เชิง relational
   - ต้องการเพียงแค่ serialize และ deserialize ข้อมูล (เช่น JSON, XML, YAML)
   - ต้องการจัดเก็บข้อมูลปริมาณมหาศาล

---

## หัวข้อที่ 3: การขยายแนวตั้ง เทียบกับ การขยายแนวนอน (Vertical vs Horizontal Scaling)
### การขยายแนวตั้ง (Vertical Scaling)
- เพิ่มทรัพยากร (CPU, RAM) ให้กับเซิร์ฟเวอร์ที่มีอยู่เดิม
- ถูกจำกัดด้วยข้อจำกัดทางฮาร์ดแวร์ และไม่มีความซ้ำซ้อน (redundancy)

### การขยายแนวนอน (Horizontal Scaling)
- เพิ่มจำนวนเซิร์ฟเวอร์เข้าไปในกลุ่ม (pool) ทำให้เหมาะสมกับระบบขนาดใหญ่มากกว่า
- ใช้ load balancer เพื่อจัดการการกระจาย request ไปยังเซิร์ฟเวอร์ต่าง ๆ

---

## หัวข้อที่ 4: Load Balancer

<div style="margin-left:3rem">
   <img src="./images/load-balancer.png" width="400" />
</div>

**Load balancer** ทำหน้าที่กระจายทราฟฟิกไปยังเซิร์ฟเวอร์หลายตัว ประโยชน์ที่ได้รับมีดังนี้:
1. ความซ้ำซ้อน (Redundancy): หากเซิร์ฟเวอร์ตัวหนึ่งล่มหรือหลุดออฟไลน์ ทราฟฟิกจะถูกส่งไปยังเซิร์ฟเวอร์ตัวอื่นแทน
   - หากเซิร์ฟเวอร์ 1 หลุดออฟไลน์ ทราฟฟิกทั้งหมดจะถูก route ไปยังเซิร์ฟเวอร์ 2
2. ความสามารถในการขยาย (Scalability): สามารถเพิ่มเซิร์ฟเวอร์ได้ง่ายเพื่อรองรับทราฟฟิกที่พุ่งสูงขึ้น
   - หากทราฟฟิกของเว็บไซต์เติบโตอย่างรวดเร็ว สามารถเพิ่มเซิร์ฟเวอร์เพิ่มเติมเข้ามาเพื่อรองรับทราฟฟิกส่วนเกินได้

## หัวข้อที่ 5: การทำสำเนาฐานข้อมูล (Database Replication)

<div style="margin-left:3rem">
   <img src="./images/database-replication.png" width="400" />
</div>

### รูปแบบ Master-Slave (Master-Slave Model)
- **ฐานข้อมูล Master:** จัดการกับ operation ที่เป็นการเขียน (write)
   - คำสั่งที่ทำการแก้ไขข้อมูล เช่น insert, delete หรือ update ทั้งหมดต้องถูกส่งไปยัง master database
- **ฐานข้อมูล Slave:** จัดการกับ operation ที่เป็นการอ่าน (read) ซึ่งช่วยเพิ่มประสิทธิภาพและความน่าเชื่อถือของระบบ
   - เนื่องจากในแอปพลิเคชันส่วนใหญ่สัดส่วนของการอ่านต่อการเขียน (read-to-write ratio) นั้นสูงกว่า ดังนั้นจำนวนฐานข้อมูล slave ในระบบจึงมักจะมากกว่าจำนวนฐานข้อมูล master

### ประโยชน์ (Benefits)
1. ประสิทธิภาพที่ดีขึ้นจากการทำ read operation แบบขนาน (parallel)
2. ความพร้อมใช้งานสูง (high availability) และความน่าเชื่อถือของข้อมูล จากการมีความซ้ำซ้อน (redundancy)

### การจัดการเมื่อเกิดความล้มเหลว (Failure Handling)
- หากมี slave database เพียงตัวเดียวและตัวนั้นหลุดออฟไลน์ การอ่านข้อมูลจะถูกส่งไปยัง master database เป็นการชั่วคราว
- ในกรณีที่มี slave database หลายตัว การอ่านข้อมูลจะถูกส่งไปยัง slave database ตัวอื่นที่ยังทำงานได้ตามปกติ และจะมีการนำเซิร์ฟเวอร์ตัวใหม่มาแทนที่ตัวเก่า
- หาก master database หลุดออฟไลน์ จะมีการ promote slave database ตัวหนึ่งขึ้นมาเป็น master ตัวใหม่
- ในระบบจริง (production) slave database ที่ถูกเลือกอาจมีข้อมูลไม่เป็นปัจจุบัน (not up to date) ดังนั้นจึงต้องอัปเดตข้อมูลด้วยการรัน data recovery script (วิธีการอย่าง multi-masters และ circular replication สามารถช่วยแก้ปัญหานี้ได้)

## หัวข้อที่ 6: การแคชข้อมูล (Caching)
**แคช (Cache)** คือที่เก็บข้อมูลที่ถูกเข้าถึงบ่อย ๆ ไว้ในหน่วยความจำ (memory) เพื่อลดภาระของฐานข้อมูล ชั้นแคช (cache tier) เป็นชั้นจัดเก็บข้อมูลชั่วคราวที่มีความเร็วสูงกว่าฐานข้อมูลมาก

<div style="margin-left:3rem">
   <img src="./images/cache.png" width="500" />
</div>

### สิ่งที่ต้องพิจารณาในการทำ Caching (Caching considerations)
1. **กรณีการใช้งาน (Use case):** ควรพิจารณาใช้แคชเมื่อข้อมูลถูกอ่านบ่อย แต่ถูกแก้ไขไม่บ่อยนัก
2. **นโยบายการหมดอายุ (Expiration Policies):** เมื่อข้อมูลในแคชหมดอายุ ข้อมูลนั้นจะถูกลบออกจากแคช หากไม่มีนโยบายกำหนดวันหมดอายุ ข้อมูลที่แคชไว้จะถูกเก็บอยู่ในหน่วยความจำแบบถาวร
3. **ความสอดคล้องของข้อมูล (Consistency):** หมายถึงการทำให้ข้อมูลในฐานข้อมูลและในแคชตรงกันอยู่เสมอ ความไม่สอดคล้องกัน (inconsistency) อาจเกิดขึ้นได้ เนื่องจาก operation ที่แก้ไขข้อมูลในฐานข้อมูลและในแคชไม่ได้อยู่ใน transaction เดียวกัน
4. **การลดผลกระทบจากความล้มเหลว (Mitigating failures):** เซิร์ฟเวอร์แคชเพียงตัวเดียวถือเป็นจุดที่อาจเกิดความล้มเหลวได้ทั้งระบบ (single point of failure) จึงแนะนำให้มีเซิร์ฟเวอร์แคชหลายตัวกระจายอยู่ในหลาย data center เพื่อหลีกเลี่ยง SPOF
5. **นโยบายการเอาข้อมูลออก (Eviction Policies):** เมื่อแคชเต็ม จำเป็นต้องเอาข้อมูลบางส่วนออก (evict) เพื่อเปิดพื้นที่ว่างในหน่วยความจำ LRU (Least Recently Used) เป็นนโยบายการ evict cache ที่นิยมใช้มากที่สุด

## หัวข้อที่ 7: Content Delivery Network (CDN)
**CDN** ช่วยเพิ่มความเร็วในการโหลดหน้าเว็บ โดยการแคช static content (รูปภาพ, CSS, JavaScript) ไว้บนเซิร์ฟเวอร์ที่กระจายอยู่ตามพื้นที่ทางภูมิศาสตร์ต่าง ๆ

<div style="margin-left:3rem">
   <img src="./images/cdn.png" width="400" />
</div>

### ขั้นตอนการทำงาน (Workflow)
1. ผู้ใช้ร้องขอเนื้อหาจากเซิร์ฟเวอร์ CDN ที่อยู่ใกล้ที่สุด
2. หากไม่มีข้อมูลอยู่ในเซิร์ฟเวอร์นั้น จะไปดึงเนื้อหาจาก origin server มาแล้วจึงแคชไว้

### สิ่งที่ต้องพิจารณาเกี่ยวกับ CDN (CDN considerations)
1. **ค่าใช้จ่าย (Cost):** CDN ถูกดำเนินการโดยผู้ให้บริการภายนอก (third-party) ซึ่งจะคิดค่าใช้จ่ายจากการรับส่งข้อมูลเข้าและออกจาก CDN
2. **ระยะเวลาหมดอายุของแคช (Cache Expiry):** ระยะเวลาหมดอายุของแคชไม่ควรนานเกินไปหรือสั้นเกินไป
3. **การสำรอง (Fallback) เมื่อ CDN มีปัญหา:** หาก CDN ขัดข้องชั่วคราว ไคลเอนต์ควรสามารถตรวจจับปัญหาได้ และร้องขอทรัพยากรจาก origin server แทน
4. **การล้างความถูกต้องของไฟล์ (Invalidating files):** หากมีการอัปเดตไฟล์ ควรทำการ invalidate แคชเพื่อให้ชี้ไปยังไฟล์เวอร์ชันที่อัปเดตแล้ว

## หัวข้อที่ 8: ชั้นเว็บแบบไม่เก็บสถานะ (Stateless Web Tier)
การย้ายข้อมูล session ไปเก็บไว้ใน datastore ที่ใช้งานร่วมกัน (shared datastore) ทำให้เว็บเซิร์ฟเวอร์กลายเป็นแบบ stateless ซึ่งช่วยให้:
1. สามารถทำ horizontal scaling ได้ง่ายขึ้น
2. สามารถทำ auto-scaling ตามปริมาณทราฟฟิกได้

## หัวข้อที่ 9: การตั้งค่าหลาย Data Center (Multi-Data Center Setup)
การ deploy ระบบไปยังหลาย data center ช่วยเพิ่มความพร้อมใช้งาน (availability) และลด latency กลยุทธ์ที่ใช้ ได้แก่:

<div style="margin-left:3rem">
   <img src="./images/data-center.png" width="400" />
</div>

1. **การ Routing ด้วย GeoDNS:** นำผู้ใช้ไปยัง data center ที่อยู่ใกล้ที่สุด
2. **การทำสำเนาข้อมูล (Data Replication):** ทำการซิงค์ข้อมูลระหว่าง data center เพื่อป้องกันความไม่สอดคล้องกันของข้อมูล

### สิ่งสำคัญที่ต้องพิจารณา (Key considerations)
- **การเปลี่ยนเส้นทางทราฟฟิก (Traffic redirection):** จำเป็นต้องมีเครื่องมือที่มีประสิทธิภาพในการนำทราฟฟิกไปยัง data center ที่ถูกต้อง
- **การซิงค์ข้อมูล (Data synchronization):** กลยุทธ์ทั่วไปคือการทำสำเนาข้อมูลไปยังหลาย data center
- **การทดสอบและการ deploy (Test and deployment):** เครื่องมือ deploy แบบอัตโนมัติมีความสำคัญมากในการรักษาความสอดคล้องของบริการในทุก data center

## หัวข้อที่ 10: Message Queue
**Message queue** คือคอมโพเนนต์ที่คงทน (durable) จัดเก็บอยู่ในหน่วยความจำ ซึ่งรองรับการสื่อสารแบบอะซิงโครนัส (asynchronous) ทำหน้าที่เป็นบัฟเฟอร์และกระจาย request แบบ asynchronous

<div style="margin-left:3rem">
   <img src="./images//message-queue.png" width="500" />
</div>

- บริการที่ส่งข้อมูลเข้ามา เรียกว่า producer/publisher จะสร้างข้อความ (message) และส่ง (publish) เข้าไปใน message queue
- บริการอื่น ๆ เรียกว่า consumer/subscriber จะเชื่อมต่อเข้ากับ queue และดำเนินการตามที่ระบุไว้ในข้อความนั้น

### ความสำคัญ (Importance)
1. **Logging:** ใช้ติดตามข้อผิดพลาด (error) และสุขภาพของระบบ (system health)

3. **Automation:** ช่วยให้การทดสอบ, การ deploy และการขยายระบบเป็นไปอย่างราบรื่น

## หัวข้อที่ 12: การขยายฐานข้อมูล (Database Scaling)
### การขยายแนวตั้ง (Vertical Scaling)
- เพิ่มทรัพยากรฮาร์ดแวร์ แต่มีข้อจำกัดทั้งด้านกายภาพและค่าใช้จ่าย
- มีข้อเสียหลายประการ:
   - มีความเสี่ยงสูงขึ้นที่จะเกิด single point of failure
   - ค่าใช้จ่ายโดยรวมของการทำ vertical scaling สูง

### การขยายแนวนอน (Horizontal Scaling / Sharding)

- แบ่งข้อมูลออกเป็นหลาย shard โดยใช้ key (เช่น `user_id`)
   - Sharding คือการแบ่งฐานข้อมูลขนาดใหญ่ออกเป็นส่วนย่อย ๆ ที่จัดการได้ง่ายขึ้น เรียกว่า shard
   - แต่ละ shard ใช้ schema เดียวกัน แต่ข้อมูลจริงในแต่ละ shard จะไม่ซ้ำกันและเป็นของ shard นั้น ๆ โดยเฉพาะ
- Sharding key มีความสำคัญมากเมื่อนำกลยุทธ์ sharding มาใช้งาน การเลือก key ที่สามารถกระจายข้อมูลได้อย่างสม่ำเสมอ (evenly) เป็นสิ่งสำคัญ

#### ความท้าทาย (Challenges)
1. **การทำ Resharding ข้อมูล:** จำเป็นต้องทำ resharding เมื่อ:
   - shard เดียวไม่สามารถรองรับข้อมูลที่เพิ่มขึ้นอย่างรวดเร็วได้อีกต่อไป
   - shard บางตัวอาจประสบปัญหาพื้นที่หมด (shard exhaustion) เร็วกว่าตัวอื่น เนื่องจากการกระจายข้อมูลที่ไม่สม่ำเสมอ
   - Consistent Hashing ถูกนำมาใช้เพื่อแก้ปัญหาเหล่านี้

2. **ปัญหา Celebrity (Celebrity problem):** การเข้าถึง shard ใดตัวหนึ่งมากเกินไปอาจทำให้เซิร์ฟเวอร์นั้นทำงานหนักเกินไป (overload)
   - วิธีแก้ปัญหานี้คือ อาจต้องจัดสรร shard แยกต่างหากสำหรับ "คนดัง" (celebrity) แต่ละราย

3. **การทำ Join และ De-normalization:** เมื่อฐานข้อมูลถูกแบ่ง shard ไปยังหลายเซิร์ฟเวอร์แล้ว การทำ join ข้าม shard จะทำได้ยาก
   - วิธีแก้ปัญหาที่นิยมใช้คือการทำ de-normalize ฐานข้อมูล เพื่อให้สามารถ query ข้อมูลได้จากตารางเดียว

## บทสรุป (Conclusion)
### สิ่งสำคัญที่ควรจำ (Key Takeaways)
1. รักษาให้ web tier เป็นแบบ stateless
2. สร้างความซ้ำซ้อน (redundancy) ในทุกชั้นของระบบ
3. ใช้ caching และ CDN เพื่อเพิ่มประสิทธิภาพ
4. ขยายชั้นข้อมูล (data tier) ด้วยวิธี sharding
5. แยกส่วนคอมโพเนนต์ (decouple) ออกจากกัน เพื่อความยืดหยุ่น

บทนี้เป็นพื้นฐานที่มั่นคงสำหรับการสร้างระบบที่สามารถขยายตัว (scalable) เพื่อรองรับผู้ใช้งานหลักล้านคนได้
