# บทที่ 18: Google Maps

## บทนำ

เราจะออกแบบเวอร์ชันอย่างง่ายของ **Google Maps**

ข้อมูลข้อเท็จจริงบางอย่างเกี่ยวกับ Google Maps:
 * เริ่มต้นในปี 2005
 * ให้บริการหลากหลาย - ภาพถ่ายดาวเทียม (satellite imagery), แผนที่ถนน, สภาพการจราจรแบบเรียลไทม์, การวางแผนเส้นทาง (route planning)
 * ภายในปี 2021 มีผู้ใช้งานต่อวัน (daily active users) 1 พันล้านคน ครอบคลุม 99% ของทั่วโลก และมีการอัปเดตตำแหน่งแบบเรียลไทม์ 25 ล้านครั้งต่อวัน

## ขั้นตอนที่ 1: ทำความเข้าใจปัญหาและกำหนดขอบเขตการออกแบบ (Understand the Problem and Establish Design Scope)

ตัวอย่างบทสนทนาถาม-ตอบระหว่างผู้สมัครกับผู้สัมภาษณ์:
 * C: เรากำลังรับมือกับผู้ใช้งานต่อวันจำนวนเท่าไหร่?
 * I: 1 พันล้าน DAU
 * C: เราควรโฟกัสที่ฟีเจอร์ไหนบ้าง?
 * I: การอัปเดตตำแหน่ง (location update), การนำทาง (navigation), ETA, การเรนเดอร์แผนที่ (map rendering)
 * C: ข้อมูลถนนมีขนาดใหญ่แค่ไหน? เรามีสิทธิ์เข้าถึงข้อมูลนี้หรือไม่?
 * I: เราได้รับข้อมูลถนนมาจากหลายแหล่ง มันมีขนาดหลาย TB ของข้อมูลดิบ
 * C: เราควรนำสภาพการจราจรมาพิจารณาด้วยไหม?
 * I: ใช่ เราควรพิจารณา เพื่อให้ประมาณการเวลาได้แม่นยำ
 * C: แล้วโหมดการเดินทางที่ต่างกัน - เดินเท้า, ปั่นจักรยาน, ขับรถล่ะ?
 * I: เราควรรองรับโหมดเหล่านั้น
 * C: แล้วเส้นทางแบบแวะหลายจุด (multi-stop directions) ล่ะ?
 * I: ให้เราไม่โฟกัสตรงนั้นในขอบเขตของการสัมภาษณ์นี้
 * C: สถานที่ธุรกิจและรูปภาพล่ะ?
 * I: คำถามที่ดี แต่ไม่จำเป็นต้องพิจารณาสิ่งเหล่านั้น

เราจะโฟกัสที่ฟีเจอร์หลักสามอย่าง - การอัปเดตตำแหน่งผู้ใช้ (user location update), บริการนำทาง (navigation service) รวมถึง ETA, และการเรนเดอร์แผนที่ (map rendering)

### **ความต้องการที่ไม่ใช่ฟังก์ชันการทำงาน (Non-functional requirements)**

- **ความแม่นยำ (Accuracy)**: ผู้ใช้ไม่ควรได้รับเส้นทางที่ผิด
- **การนำทางที่ราบรื่น (Smooth navigation)**: ผู้ใช้ควรได้รับประสบการณ์การเรนเดอร์แผนที่ที่ราบรื่น
- **การใช้ข้อมูลและแบตเตอรี่ (Data and battery usage)**: ไคลเอนต์ควรใช้ข้อมูลและแบตเตอรี่ให้น้อยที่สุดเท่าที่จะทำได้ ซึ่งสำคัญมากสำหรับอุปกรณ์มือถือ
- ความพร้อมใช้งาน (availability) และความสามารถในการขยายระบบ (scalability) โดยทั่วไป

### **พื้นฐานเรื่องแผนที่ (Map 101)**

ก่อนจะเข้าสู่การออกแบบ มีแนวคิดเกี่ยวกับแผนที่บางอย่างที่เราควรทำความเข้าใจก่อน

#### การแปลงจาก 3 มิติ ไป 2 มิติ (Going from 3D to 2D)

กระบวนการแปลงจุดต่าง ๆ จากระนาบ 3D ไปเป็นระนาบ 2D เรียกว่า "การฉายภาพแผนที่ (map projection)"

มีวิธีการทำหลายแบบ ซึ่งแต่ละแบบก็มีข้อดีข้อเสียของตัวเอง เกือบทั้งหมดจะทำให้เกิดการบิดเบือนของรูปทรงเรขาคณิตจริง

<div style="margin-left:3rem">
    <img src="./images/map-projections.png" alt="map-projections" width="500" />
</div>

Google Maps เลือกใช้เวอร์ชันดัดแปลงของการฉายภาพแบบ Mercator ที่เรียกว่า "Web Mercator"

#### การแปลงที่อยู่เป็นพิกัด (Geocoding)

Geocoding คือกระบวนการแปลงที่อยู่ (addresses) ให้เป็นพิกัดทางภูมิศาสตร์ (geographic coordinates)

กระบวนการย้อนกลับเรียกว่า "reverse geocoding"

วิธีหนึ่งในการทำสิ่งนี้คือการใช้การประมาณค่าในช่วง (interpolation) - โดยอาศัยข้อมูลจากแหล่งต่าง ๆ (เช่น GIS) ซึ่งเครือข่ายถนนถูกแมปเข้ากับพื้นที่พิกัดภูมิศาสตร์

#### การเข้ารหัสตำแหน่งทางภูมิศาสตร์ (Geohashing)

Geohashing เป็นระบบการเข้ารหัสซึ่งเข้ารหัสพื้นที่ทางภูมิศาสตร์ให้เป็นสตริงของตัวอักษรและตัวเลข

มันแสดงโลกเป็นพื้นผิวที่ถูกทำให้แบนราบ และแบ่งย่อยแบบวนซ้ำ (recursively) ออกเป็นสี่ส่วน (quadrants):

</div>

#### การเรนเดอร์แผนที่ (Map rendering)

การเรนเดอร์แผนที่เกิดขึ้นผ่านการทำ tiling แทนที่จะเรนเดอร์แผนที่ทั้งหมดเป็นภาพขนาดใหญ่ภาพเดียว โลกจะถูกแบ่งออกเป็น tile ขนาดเล็กกว่า

ไคลเอนต์จะดาวน์โหลดเฉพาะ tile ที่เกี่ยวข้องและเรนเดอร์มันเหมือนกับการต่อโมเสก (mosaic) เข้าด้วยกัน

มี tile ที่แตกต่างกันสำหรับแต่ละระดับการซูม (zoom level) ไคลเอนต์จะเลือก tile ที่เหมาะสมตามระดับการซูมของไคลเอนต์เอง

ตัวอย่างเช่น เมื่อซูมออกจนเห็นทั้งโลก จะดาวน์โหลดเพียง tile ขนาด 256x256 พิกเซลเพียงตัวเดียว ซึ่งเป็นตัวแทนของทั้งโลก

#### การประมวลผลข้อมูลถนนสำหรับอัลกอริทึมการนำทาง (Road data processing for navigation algorithms)

ในอัลกอริทึมการหาเส้นทาง (routing algorithms) ส่วนใหญ่ ทางแยกจะถูกแทนด้วยโหนด (nodes) และถนนจะถูกแทนด้วยเส้นเชื่อม (edges):

<div style="margin-left:3rem">
    <img src="./images/road-representation.png" alt="road-representation" width="500" />
</div>

อัลกอริทึมการนำทางส่วนใหญ่ใช้เวอร์ชันดัดแปลงของอัลกอริทึม Djikstra หรือ A*

ประสิทธิภาพของการหาเส้นทาง (pathfinding) นั้นไวต่อขนาดของกราฟ (graph) มาก เพื่อให้ทำงานได้ในระดับสเกลใหญ่ เราไม่สามารถแทนทั้งโลกเป็นกราฟเดียวแล้วรันอัลกอริทึมบนกราฟนั้นได้

แทนที่จะทำแบบนั้น เราใช้เทคนิคที่คล้ายกับการทำ tiling - เราแบ่งย่อยโลกออกเป็นกราฟที่เล็กลงเรื่อย ๆ

Routing tile จะเก็บ reference ไปยัง tile ข้างเคียง และอัลกอริทึมสามารถต่อกราฟถนนที่ใหญ่ขึ้นได้ขณะที่ไล่ผ่าน (traverse) tile ที่เชื่อมต่อกันเหล่านั้น:

<div style="margin-left:3rem">
    <img src="./images/routing-tiles.png" alt="routing-tiles" width="500" />
</div>

เทคนิคนี้ช่วยให้เราลด memory bandwidth ได้อย่างมาก และโหลดเฉพาะ tile ที่จำเป็นสำหรับคู่ต้นทาง/ปลายทางที่กำหนด

อย่างไรก็ตาม สำหรับเส้นทางที่ยาวขึ้น การต่อ routing tile ขนาดเล็กที่มีรายละเอียดสูงเข้าด้วยกันก็ยังคงกินเวลา/หน่วยความจำมากอยู่ดี แทนที่จะทำแบบนั้น เรามี routing tile ที่มีระดับรายละเอียด (level of detail) แตกต่างกัน และอัลกอริทึมจะใช้ tile ที่มีความละเอียดเหมาะสม ตามปลายทางที่เรากำลังมุ่งหน้าไป:

### **การประมาณการคร่าว ๆ (Back-of-the-envelope estimation)**

สำหรับการจัดเก็บข้อมูล (storage) เราต้องเก็บ:
 * แผนที่ของโลก - ประมาณการอยู่ที่ ~70PB โดยอิงจาก tile ทั้งหมดที่เราต้องเก็บ แต่คำนวณรวมการบีบอัด (compression) ของ tile ที่คล้ายกันมาก ๆ (เช่น ทะเลทรายกว้างใหญ่) เข้าไปด้วย
 * เมตาดาต้า (metadata) - มีขนาดเล็กมากจนไม่สำคัญ ดังนั้นเราสามารถข้ามการคำนวณส่วนนี้ได้
 * ข้อมูลถนน (Road info) - จัดเก็บในรูปแบบ routing tile

การประมาณ QPS สำหรับ request ด้านการนำทาง - ผู้ใช้ต่อวัน 1 พันล้านคน ใช้งาน 35 นาทีต่อสัปดาห์ -> 5 พันล้านนาทีต่อวัน
สมมติว่า request การอัปเดต GPS ถูกจัดกลุ่ม (batched) เราจะได้ 200k QPS และ 1 ล้าน QPS ที่ peak load

### **บริการตำแหน่ง (Location service)**

<div style="margin-left:3rem">
    <img src="./images/location-service.png" alt="location-service" width="500" />
</div>

รับผิดชอบในการบันทึกการอัปเดตตำแหน่งของผู้ใช้:
 * การอัปเดตตำแหน่งถูกส่งทุก ๆ `t` วินาที
 * สตรีมข้อมูลตำแหน่ง (location data streams) สามารถนำมาใช้ปรับปรุงบริการนี้เมื่อเวลาผ่านไปได้ เช่น ให้ ETA ที่แม่นยำขึ้น, เฝ้าติดตามข้อมูลการจราจร, ตรวจจับถนนที่ปิด, วิเคราะห์พฤติกรรมผู้ใช้ เป็นต้น

แทนที่จะส่งการอัปเดตตำแหน่งไปยังเซิร์ฟเวอร์ตลอดเวลา เราสามารถจัดกลุ่ม (batch) การอัปเดตที่ฝั่งไคลเอนต์แล้วส่งเป็นชุด (batch) แทนได้:

<div style="margin-left:3rem">
    <img src="./images/location-update-batches.png" alt="location-update-batches" width="500" />
</div>

แม้จะมีการปรับปรุงนี้ แต่สำหรับระบบขนาดใหญ่ระดับ Google Maps ภาระโหลดก็ยังคงมีนัยสำคัญอยู่ ดังนั้นเราสามารถใช้ฐานข้อมูลที่ optimize สำหรับการเขียนหนัก (heavy writes) เช่น Cassandra

เรายังสามารถใช้ Kafka สำหรับการประมวลผลสตรีม (stream processing) การอัปเดตตำแหน่งอย่างมีประสิทธิภาพ เพื่อนำไปวิเคราะห์เพิ่มเติมได้

ตัวอย่าง payload ของ request การอัปเดตตำแหน่ง:

```
POST /v1/locations
Parameters
  locs: JSON encoded array of (latitude, longitude, timestamp) tuples.
```

### **บริการนำทาง (Navigation service)**

คอมโพเนนต์นี้รับผิดชอบในการหาเส้นทางที่รวดเร็วระหว่างจุด A และ B ภายในเวลาที่สมเหตุสมผล (latency เล็กน้อยยอมรับได้) เส้นทางไม่จำเป็นต้องเร็วที่สุด แต่ความแม่นยำเป็นสิ่งสำคัญ

ตัวอย่าง payload ของ request:

```
GET /v1/nav?origin=1355+market+street,SF&destination=Disneyland
```

การเปลี่ยนแปลงของการจราจรและการเปลี่ยนเส้นทางใหม่ (reroutes) ยังไม่ถูกนำมาพิจารณาในตอนนี้ สิ่งเหล่านั้นจะถูกจัดการในหัวข้อการเจาะลึก (deep dive)

### **การเรนเดอร์แผนที่ (Map rendering)**

การเก็บชุดข้อมูลของ mapping tile ทั้งหมดไว้ที่ฝั่งไคลเอนต์เป็นไปไม่ได้ในทางปฏิบัติ เนื่องจากมีขนาดหลายเพตะไบต์ (petabytes)

จำเป็นต้องดึงข้อมูลเหล่านี้มาตามคำขอ (on-demand) จากเซิร์ฟเวอร์ โดยอิงตามตำแหน่งและระดับการซูมของไคลเอนต์

เมื่อไหร่ที่ควรดึง tile ใหม่ - ขณะที่ผู้ใช้ซูมเข้า/ออก และระหว่างการนำทาง ขณะที่พวกเขากำลังมุ่งหน้าไปยัง tile ใหม่

tile แผนที่ควรถูกส่งให้ไคลเอนต์อย่างไร?
 * สามารถสร้างขึ้นแบบไดนามิกได้ แต่จะสร้างภาระโหลดมหาศาลบนเซิร์ฟเวอร์ และยังทำให้การทำแคชยากขึ้นด้วย
 * tile แผนที่ถูกให้บริการแบบสถิต (static) โดยอิงตาม geohash ของมัน ซึ่งไคลเอนต์สามารถคำนวณได้เอง สามารถจัดเก็บและให้บริการแบบสถิตจาก CDN ได้

</div>

ตัวเลือกที่ต้องพิจารณาสำหรับการกำหนด map tile:
 * geohash สำหรับ map tile สามารถคำนวณได้ที่ฝั่งไคลเอนต์ หากเป็นเช่นนั้น เราควรระมัดระวังเนื่องจากเราต้องยึดติดกับวิธีการคำนวณ map tile แบบนี้ในระยะยาว เพราะการบังคับให้ไคลเอนต์อัปเดตนั้นทำได้ยาก
 * อีกทางเลือกหนึ่งคือ เราสามารถมี API แบบง่าย ๆ ซึ่งคำนวณ URL ของ map tile แทนไคลเอนต์ โดยแลกมาด้วยการเรียก API เพิ่มเติม

### **โมเดลข้อมูล (Data model)**

มาพูดถึงกันว่าเราจัดเก็บข้อมูลประเภทต่าง ๆ ที่เรากำลังจัดการอยู่นี้อย่างไร

#### Routing tile

ชุดข้อมูลถนนเริ่มต้นได้มาจากแหล่งต่าง ๆ และถูกปรับปรุงให้ดีขึ้นเมื่อเวลาผ่านไป โดยอิงตามข้อมูลการอัปเดตตำแหน่ง

ข้อมูลถนนไม่มีโครงสร้าง (unstructured) เรามี pipeline การประมวลผลแบบออฟไลน์ (offline) ที่ทำงานเป็นระยะ ซึ่งแปลงข้อมูลดิบนี้ให้เป็น routing tile แบบกราฟที่แอปของเราต้องการ

แทนที่จะเก็บ tile เหล่านี้ในฐานข้อมูล เนื่องจากเราไม่ต้องการฟีเจอร์ใด ๆ ของฐานข้อมูล เราสามารถเก็บไว้ใน S3 object storage แทน พร้อมกับทำแคชอย่างเข้มข้น (aggressively)

เรายังสามารถใช้ไลบรารีเพื่อบีบอัด adjacency list ให้เป็นไฟล์ไบนารีได้อย่างมีประสิทธิภาพ

#### ข้อมูลตำแหน่งผู้ใช้ (User location data)

ข้อมูลตำแหน่งผู้ใช้มีประโยชน์มากสำหรับการอัปเดตสภาพการจราจรและการวิเคราะห์ประเภทอื่น ๆ อีกมากมาย

เราสามารถใช้ Cassandra สำหรับจัดเก็บข้อมูลประเภทนี้ เนื่องจากธรรมชาติของมันคือมีการเขียนหนัก (write-heavy)

#### บริการตำแหน่ง (Location service)

มาโฟกัสที่การออกแบบฐานข้อมูลและวิธีการจัดเก็บตำแหน่งผู้ใช้อย่างละเอียดสำหรับบริการนี้กัน

เราจะเลือก Cassandra เป็นตัวเลือกฐานข้อมูลของเรา เนื่องจากเข้ากับความต้องการทั้งหมดของเราได้อย่างลงตัว

#### บริการนำทาง (Navigation service)

บริการนี้รับผิดชอบในการหาเส้นทางที่เร็วที่สุด:

มาไล่ดูแต่ละคอมโพเนนต์ในระบบย่อยนี้กัน

อันดับแรก เรามีบริการ geocoding ซึ่งแปลงที่อยู่ให้เป็นตำแหน่งของคู่ lat/long

```
https://maps.googleapis.com/maps/api/geocode/json?address=1600+Amphitheatre+Parkway,+Mountain+View,+CA
```

```json
{
   "results" : [
      {
         "formatted_address" : "1600 Amphitheatre Parkway, Mountain View, CA 94043, USA",
         "geometry" : {
            "location" : {
               "lat" : 37.4224764,
               "lng" : -122.0842499
            },
            "location_type" : "ROOFTOP",
            "viewport" : {
               "northeast" : {
                  "lat" : 37.4238253802915,
                  "lng" : -122.0829009197085
               },
               "southwest" : {
                  "lat" : 37.4211274197085,

            "compound_code": "CWC8+W5 Mountain View, California, United States",
            "global_code": "849VCWC8+W5"
         },

      }
   ],
   "status" : "OK"
```

บริการ route planner คำนวณเส้นทางที่แนะนำ ซึ่ง optimize สำหรับเวลาเดินทางตามสภาพการจราจรปัจจุบัน

บริการ shortest-path รันตัวแปรหนึ่งของอัลกอริทึม A* กับ routing tile ใน object storage เพื่อคำนวณเส้นทางที่เหมาะสมที่สุด:
 * มันรับคู่ต้นทาง/ปลายทาง แปลงให้เป็นคู่ lat/long และคำนวณ geohash จากคู่พิกัดเหล่านั้นเพื่อระบุ routing tile ที่เกี่ยวข้อง
 * อัลกอริทึมเริ่มต้นจาก routing tile เริ่มต้น และเริ่มไล่ผ่าน (traverse) จนกว่าจะพบเส้นทางที่ดีพอไปยัง tile ปลายทาง

<div style="margin-left:3rem">
    <img src="./images/shortest-path-service.png" alt="shortest-path-service" width="500" />
</div>

บริการ ETA ถูกเรียกโดย route planner เพื่อให้เวลาโดยประมาณ โดยอิงจากอัลกอริทึม machine learning ที่คาดการณ์ ETA จากข้อมูลการจราจร

บริการ ranker รับผิดชอบในการจัดอันดับเส้นทางที่เป็นไปได้ต่าง ๆ โดยอิงตามตัวกรอง (filters) ที่ผู้ใช้ส่งมา เช่น flag เพื่อหลีกเลี่ยงถนนที่มีด่านเก็บเงิน (toll roads) หรือทางด่วน (freeways)

บริการ updater จะอัปเดตฐานข้อมูลสำคัญบางส่วนแบบ asynchronous เพื่อให้ข้อมูลเป็นปัจจุบันอยู่เสมอ

#### การปรับปรุง - ETA แบบปรับตัวได้และการเปลี่ยนเส้นทางใหม่ (Improvement - adaptive ETA and rerouting)

การปรับปรุงอย่างหนึ่งที่เราทำได้คือ การอัปเดตเส้นทางที่กำลังดำเนินอยู่ (in-flight routes) แบบปรับตัวได้ (adaptively) โดยอิงตามข้อมูลการจราจรใหม่ที่มีให้ใช้งาน

วิธีหนึ่งในการนำสิ่งนี้ไปใช้คือการเก็บผู้ใช้ที่กำลังนำทางอยู่ในขณะนั้นไว้ในฐานข้อมูล โดยเก็บ tile ทั้งหมดที่พวกเขาควรจะผ่าน

ข้อมูลอาจมีลักษณะดังนี้:

```
user_1: r_1, r_2, r_3, …, r_k
user_2: r_4, r_6, r_9, …, r_n
user_3: r_2, r_8, r_9, …, r_m
...
user_n: r_2, r_10, r21, ..., r_l
```

หากเกิดอุบัติเหตุจราจรบน tile ใด tile หนึ่ง เราสามารถระบุผู้ใช้ทั้งหมดที่เส้นทางของพวกเขาผ่าน tile นั้น และเปลี่ยนเส้นทางให้พวกเขาใหม่ได้

เพื่อลดจำนวน tile ที่เราต้องเก็บในฐานข้อมูล เราสามารถเก็บเฉพาะ routing tile ต้นทาง และ routing tile หลายตัวในระดับความละเอียด (resolution) ต่าง ๆ จนกระทั่ง tile ปลายทางถูกรวมเข้ามาด้วยแทน:

```
user_1, r_1, super(r_1), super(super(r_1)), ...
```

<div style="margin-left:3rem">
    <img src="./images/adaptive-eta-data-storage.png" alt="adaptive-eta-data-storage" width="500" />
</div>

ด้วยวิธีนี้ เราเพียงแค่ต้องตรวจสอบว่า tile สุดท้ายของผู้ใช้รวม tile ที่เกิดอุบัติเหตุจราจรหรือไม่ เพื่อดูว่าผู้ใช้ได้รับผลกระทบหรือไม่

เรายังสามารถติดตามเส้นทางที่เป็นไปได้ทั้งหมดสำหรับผู้ใช้ที่กำลังนำทางอยู่ และแจ้งเตือนพวกเขาหากมีเส้นทางใหม่ที่เร็วกว่า

#### โปรโตคอลการส่งข้อมูล (Delivery protocols)

เรามีตัวเลือกหลายอย่างที่ช่วยให้เราสามารถ push ข้อมูลจากเซิร์ฟเวอร์ไปยังไคลเอนต์ได้เชิงรุก (proactively):
 * การแจ้งเตือนแบบ push บนมือถือ (mobile push notifications) ใช้ไม่ได้ เพราะ payload มีข้อจำกัด และไม่รองรับสำหรับเว็บแอป
 * WebSocket โดยทั่วไปเป็นตัวเลือกที่ดีกว่า long-polling เนื่องจากมีการใช้ทรัพยากรประมวลผล (compute footprint) บนเซิร์ฟเวอร์น้อยกว่า
 * เรายังสามารถใช้ server-sent events (SSE) ได้ แต่มีแนวโน้มเลือกใช้ web socket มากกว่า เนื่องจากรองรับการสื่อสารแบบสองทาง (bi-directional) ซึ่งอาจมีประโยชน์สำหรับฟีเจอร์อย่างเช่น การส่งมอบระยะสุดท้าย (last-mile delivery)
